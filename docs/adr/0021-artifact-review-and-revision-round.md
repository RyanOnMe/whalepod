# ADR-0021：交付物审阅批注、修订批次与新版关联

- 状态：已采纳（2026-10-23；实现按三个纵向切片推进，协议与 migration 按仓库纪律两名独立评审后合入）
- 日期：2026-10-23
- 来源：《WhalePod 交接待办与交付物审阅交互方案》（2026-10-23）

## 问题

现有交付物只有「文件卡 + 受控下载 + 整件文本预览」与「以整件 Artifact 为输入的复核/
修订 Run」。成员仍要靠截图、复制意见、切到 Agent 重述要求，再回到页面核对新版；系统
没有表达「针对某个已发布版本的某处意见」「本轮修订处理了哪些意见」「哪份新候选对应
哪份原稿」这三件事。若直接复用讨论消息：意见与版本脱钩、无法逐条复核、后来补充的
意见会混进已启动的执行；若按文件名猜新版本：证据链不成立。

## 决定

### 1. 审阅对象是不可变的已发布 Artifact 版本

- 团队审阅只针对 `status='published'` 的 Artifact；候选仍仅拥有者可见，拥有者检查
  候选走既有「检查候选」路径，不是团队审阅。
- 版本身份就是 Artifact 行本身：`artifact_id` + `sha256` 在创建时固定，不存在原地
  更新。新版是**另一件** Artifact；关联靠显式版本链（§5），不靠文件名、标题或时间。
- 「发布」只表示团队可见，不等于定稿；审阅邀请、批注、提交意见都不改变任务状态、
  不授予执行或审批权限。

### 2. 新增实体

- **审阅邀请** `artifact_review_invitation`：固定 `artifact_id`、邀请人、审阅人、
  可选「请重点看什么」。每人每版本至多一条；状态只表达 `pending`（待提交意见）与
  `submitted`（已提交/本轮无意见）。邀请不建下游 Task、不产生「仅受邀者可见」的
  新权限；文件仍按当前团队可见规则读取。
- **批注线程** `artifact_comment`：固定 `artifact_id`、作者、`kind`
  （`whole` | `text` | `region`）、锚点 JSON、正文，`parent_comment_id` 表达回复。
  批注一旦发表即持久保存，编辑不改变作者与版本。
- **修订批次** `artifact_revision_round`：由任务责任人发起，固定原稿 Artifact、
  选定批注及回复的不可变快照、参考材料清单、责任人补充方向、关联 Run（可为空，
  启动时固化）。批次启动后，后来补充的批注不进入该批次。
- **新版关联** `artifact_revision_link`：责任人把本轮候选显式关联到原稿与批次；
  一件候选至多一个关联，发布后关系固定。历史文件不按名称补造版本链。
- **批注复核** `artifact_comment_resolution`：逐条记录 `resolved` /
  `needs_work`、确认人、补充意见与所属批次；批注始终锚定原始版本，不随后续版本
  自动搬移。
- **预览绑定** `artifact_preview`：Office 等派生只读预览与原件的绑定、状态与失败
  原因。预览是阅读副本，权限继承原件；转换失败不阻止原件交付。

### 3. 权限与责任

- 读取/批注：能读取该已发布 Artifact 的团队成员都能查看与新增批注、回复；候选
  的批注仍仅拥有者可见。服务端按 Artifact 当前可见性重新判权，不以历史邀请授权。
- 邀请：任务责任人或 Artifact 拥有者可邀请已能读取该版本的成员；被邀请不等于被
  授予执行权，邀请只决定待办归属。
- 发起修订：只有任务责任人可从本轮反馈启动执行；批注创建、回复、提交意见都不
  启动 Run。
- 复核收口：批注作者确认「已解决」或「仍需修改」；责任人可写明理由后代为收口，
  并记录实际确认人。Agent 的「已处理」说明只是待核对报告，**Agent 无权关闭批注**。
- 任务完成仍由真人按既有流程确认；有未解决批注时只提示数量与入口，不新增「全部
  审阅者通过」的强制门。

### 4. 锚点与定位

- 整件批注是所有格式的基础能力，不依赖定位。
- 文本：保存 `quote` + 前后文 + 版本内偏移；客户端负责恢复位置，服务端校验所选
  文字确在该版本内容中。重复文字、换页或缩放后无法唯一恢复时，展示原引用并明确
  标注「无法定位」，不猜位置。
- 区域：PDF 保存页码与归一化矩形，图片保存归一化矩形；服务端校验页码/坐标范围。
  首版不支持 DOCX 段落、XLSX 单元格、PPTX 对象级定位，Office 文件使用整件批注并
  可写明页码或位置。
- 批注位置永远相对原始版本；新版出现后不自动搬移、不删除旧意见、不把「找不到
  位置」解释为已解决。

### 5. 修订执行：快照冻结与显式关联

- 责任人组织本轮修订时明确选择要处理的批注；未选与暂缓的意见保留。启动前展示
  原稿版本、选定意见、参考材料、Agent 与执行环境；默认定位原产出会话，无法续接
  时要求显式选择新执行，不自动沿用最近的 Reviewer。
- 启动时把原稿 Artifact 与选定意见快照写入 Run 输入（复用既有 Run 创建与单活跃
  约束），经 ADR-0020 的 `executionContext` 注入 Runtime：报告各项意见的处理方式，
  但不据此改批注状态。冻结后补充的批注进入下一轮。
- 只能由责任人把本轮候选显式关联到原稿与批次；发布候选后，参与本轮的批注人收到
  「待复核」，页面同时展示原批注、原稿位置、新版与处理说明。文本看差异，其他格式
  并排检查；不支持比较时明确说明。
- 上游/原稿更新不修改已冻结的批次输入；历史 Run 的输入与旧批注永久保留原版本。

### 6. 待办与导航

- 待办新增 `confirm_handoff`（待接收交接）、`submit_review`（待审阅）、
  `organize_feedback`（待处理反馈）、`resolve_comments`（待复核）类型，携带准确
  对象身份（receipt / artifact / round / comment），点击只导航，不自动执行业务动作。
- 交接事项与「接受任务」并存时先展示一张交接卡并标注「任务尚未接受」；理解确认后
  仍未接受则继续显示接受任务事项，不能直接消失。
- 同一任务可有多份交接：逐份可见，待办链接指向具体回执卡。任务改派时**未确认**
  回执随责任转移给新责任人（旧确认保留原确认人与版本）；旧接收人不能再确认。

### 7. 保留边界

- 首版每轮修订针对一件主交付物，可附参考材料、邀请多人审阅；多文件任务逐件处理，
  不做跨文件自动合并修订。
- 不导入/导出 Office 内部批注与修订记录；不做 Word 修订往返同步、全文协同编辑、
  自动共享会话；不改变 DSH 版本。
- 文件权限、发布、交接确认、Run 创建与审批仍由服务端按既有规则裁决；本 ADR 只新增
  审阅相关对象与派生读面，不建立第二条执行通道。

## 验证

- 两成员通过真实页面走完「发表批注 → 提交意见 → 责任人启动修订 → 发布新版 →
  批注人确认」，并覆盖无意见分支。
- 批注引用精确版本；重复文字、缩放、换页后定位正确；无法定位明确失败。
- Runtime 实际收到原稿与所选意见；未选意见、后来补充意见不进入已启动执行。
- 新版关联正确，旧版与旧批注保留；模型声称完成不会自动关闭意见。
- 未受邀成员不获得私有候选；非责任人不能通过新入口启动修订；邀请不授予执行权限。
- 重试、并发反馈、权限变化、设备离线及生成失败均不造成重复执行或假完成。
- 待办在另一成员操作后更新，点击只导航，不自动执行业务动作。
- 每类格式使用实际样本检查内容、定位和回退；Office 转换另外验证原件未变化及派生件
  权限继承。
- 相关质量门：Q0/Q1、定向 Q2/Q3、生产装配 Q5、权限负向 Q7；证据按六原语归档。

## 2026-10-26 安全评审收敛（ADR-0023）

真实外链 DOCX 可令未隔离 LibreOffice 读取工作区外图像；独立配置 profile 不构成权限边界。自动转换、派生 PDF 新上传及历史 PDF 读取均暂停，API 明确报告 ISOLATION_REQUIRED，原件下载和整件批注保留。早期转换和阅读 PASS 不代表本版本开放能力，重新开放的条件见 ADR-0023。


## 2026-10-26 评审修正：修订启动原子提交

修订批次不再在事务外持久化 `starting` 后另行创建 Run。启动命令以同一幂等事务按 **Task → round** 顺序加锁，并在 Task 锁内再次确认当前责任人。认领、既有 Run 创建核心、输入快照、Run/outbox、批次绑定、团队事件及命令回执全部同事务提交；任一异常或进程在提交前退出都会整体回滚，不留下没有 Run 的永久认领。

RunOrchestrator 的 `createWithinTransaction` 是内部组合入口，只复用原有输入校验和创建核心；不能在持有 Task 锁时调用另开事务的 `create`。调用者必须提供自己的资源锁与幂等边界。设备在线版本事实在锁前读取，以免连接池只剩当前事务连接时发生嵌套查询等待；已有 Run 的恢复不要求原设备此刻仍在线。

兼容旧单 Hub 升级遗留状态：获得 Task/round 锁后先按不可变 `run.review_input.roundId` 查找既有 Run，有则只补绑定，无则在该锁内继续同一轮创建。不采用无锁重置、定时自动重放工具或租约推断。所有新启动都遵守同一锁序，因此同键或不同键并发均至多产生本轮一个 Run。旧版 Hub 与新版 Hub 不应同时写同一数据库。
