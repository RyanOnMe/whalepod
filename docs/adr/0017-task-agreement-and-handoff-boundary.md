# ADR-0017：任务约定、交接包与跨任务输入的版本化边界

- 状态：已采纳（2026-10-18 用户批准下一版方案；实现分四个纵向批次，协议与 migration 按仓库纪律两名独立评审后合入）
- 日期：2026-10-18
- 来源：《WhalePod 下一版：让需求和成果准确传到下一个人》方案（2026-10-18）+ 总纲 Phase 3「有证据才开工」前置调整（本轮把最小产品开发与真实试用合为一轮）

## 问题

总纲成功判据是「真实团队低摩擦完成跨成员可信交接」。当前仓库只有同一 Task 内的 Run
输入快照（ADR-0016）与同一 Task 的讨论/执行分离（ADR-0010），没有表达「执行前对要求的共同
依据」「执行成果的版本化交接」「接收方的确认与固定输入」这三件事的实体。若不做版本化：
并发修改会互相覆盖；执行中改要求会悄悄改变已启动 Run 的语义；交接内容发布后仍可被改；
跨任务引用会绕过「已发布才可共享」的边界。

## 决定

### 1. 任务约定：TaskSpecRevision 是唯一正式的"要求"载体

- 内容固定四段：目标、约束、验收条件、待确认问题。**草稿（draft）不构成要求**；只有
  Task 真人责任人（`task.assignee_user_id`，Agent 受派时恒为指派人）显式确认后才冻结为
  已确认版本（`confirmed`），确认产生每 Task 单调递增的 `revision_number`。
- 每 Task 至多一个开放草稿；草稿编辑携带 `draft_version` 并发令牌，不匹配即 409——
  **并发修改不覆盖他人版本**（不引入行锁等待，冲突即重取）。
- Task 级开关 `agreement_enabled`：责任人可随时开启/关闭（开启不要求先有已确认版本——
  开启后尚无已确认版本时业务 Run 创建被明确拒绝并引导先确认，这是 `AGREEMENT_REQUIRED`
  的真实可达路径）。
  开启后该 Task 的**业务 Run 必须绑定已确认版本**；关闭后新 Run 不再要求绑定，历史 Run、
  已发布交接包与已确认版本一律不动。普通任务（开关关闭）保留现有路径。
- 整理约定的辅助 Run 以 `run.purpose='agreement_draft'` 显式标记用途，**免绑定**。
  本轮只落地用途标记与免绑定规则；Agent 提案工具（把整理结果直接落成草稿）与对应入口
  按方案最小界面之后补，不阻塞本批次。

### 2. Run 绑定：快照时点固化，全入口单点收口

- `run.spec_revision_id`（可空）：创建事务内固化；全部创建入口（手动、重跑、续跑、
  执行区指令、自动指派驱动）统一经 `RunOrchestrator` 收口，**没有任何入口可以绕过**。
- 绑定解析：显式传入的 `specRevisionId` 必须是本 Task 的已确认版本；缺省取创建时刻的
  最新已确认版本。重跑/续跑与新执行同规则（新 Run 默认采用当前已确认版本；要继承来源
  版本必须显式传来源的 `specRevisionId`，界面同时呈现两个选择）。
- 启用后缺已确认版本时业务 Run 创建被拒并给明确引导（先确认任务约定）。
- 历史 Run 的空绑定显示「未绑定」，**不补造历史**；新版本不修改任何已有 Run。执行中
  约定更新时保留当前 Run 的绑定，界面提示「有新版本」，由用户选择追问、取消或让下次
  执行采用——三者都不由系统自动执行。

### 3. 交接草稿生成边界：成员 Runtime 收尾，只读、一次、有界

- 仅在业务 Run **正常完成**（turn completed）的收尾阶段、且 Task 开启约定流程时自动生成；
  失败/取消的 Run 不调用模型。自动整理最多一次，60 秒硬超时（测试经环境变量收窄，
  非功能开关）。
- 生成调用是**一次性模型调用**（走 Run 既有 provider/model 配置，Hub 不新增模型凭据；
  经 DSH `llm` 服务而非 agent turn），不注册任何工具、不写业务事实、不改变会话与
  Run 终态。输入只用本次上下文：Run 的指令与助手输出、绑定的约定版本内容、本次
  Artifact 候选清单与提交引用；输出为结构化 JSON（完成项/接口约定/未完成项/关键决定/
  验证证据/下游行动/PR·commit 引用），超限或解析失败一律按失败处理。
- 超时或失败标记「交接草稿未生成」（关联源 Run 的失败记录），**不改变业务执行结果**；
  迟到/重发的上报事件只更新草稿侧事实，不复活终态、不重复执行任何业务工具。
- 上报沿既有 run.event 通道（owner 受众的专用变体），复用 spool/ack/resend 的断线
  恢复；草稿内容只进 owner 受众与草稿表，不进团队投影、不进 Node/Hub 日志。

### 4. 私有检查、显式发布、不可变版本

- 草稿仅源 Run owner 可见可编辑（owner 受众事件 + owner 作用域 API；**管理员亦不可见**，
  「不泄露名称、数量、内容」，存在性以 404 收口）。owner 也可手工新建/编辑草稿——
  自动生成失败或想让 Agent 从零整理时这是明确的恢复路径。
- 发布是 owner 的显式动作：产生 Task 级单调递增（`(task_id, revision_number)` 唯一约束）
  的不可变 HandoffRevision。发布校验：验证证据项必须附引用（artifact/run/url/commit）；
  材料引用只允许**已发布** Artifact（候选不可成为交接包引用，发布时复验）；来源 Run、
  约定版本、Artifact 身份与摘要由系统填入，owner 不可伪造。发布后不原地覆盖；修改
  必须产生新草稿、走新版本。
- 模型生成的叙述默认标记「待核实」；owner 逐项核对后可改标。发布动作本身不授予任何
  执行、审批或分享权限。

### 5. 跨任务输入：接收确认 + 独立快照 + 固定摘要

- 上游发布后 `deliver`：选择成员，创建或关联**同项目**下由其负责的下游 Task。交接已
  发布版本 + 下游 Task 构成接收关系（receipts 表）。接收方确认时填写「本次准备做什么」
  （必填）与可选差异（差异复用讨论，落上游 Task 的一条消息）。确认接收**不等于**接受
  Task、不自动启动 Run；接收方接受任务、确认自己的环境后显式执行。
- 下游 Run 的交接材料是**独立、显式选择**的输入：`run.handoff_input` 快照（receipt、
  上游版本号、逐件 artifactId/sha256/byteSize/sourceRunId），与同 Task 的
  `artifact_input_manifest` 互不合并、语义互不借用。创建时点固化，上游之后发布新版本
  不改变任何历史 Run 的输入。请求缺省不带交接输入；界面在存在已确认 receipt 时默认
  勾选并展示固定版本号。
- 上游更新时下游显示「有新版本」；接收方 adopt 产生**新 receipt**（理解必填），旧
  receipt 与旧 Run 保留原版本。重复点击确认/采用不重复创建 Task、receipt 或 Run
  （幂等键 + 状态早返回）。
- Node 下载按快照内固定摘要校验（sha256/byteSize，不匹配明确失败）；设备下载授权只在
  「该设备自己的 Run 的交接输入快照引用了该 Artifact」这一明确范围内扩权（现有
  deviceHasRunOnTask 之外的最小扩展），不开放上游其他材料、候选与私有现场。
- 交接引用不授予执行或审批权限：Run 创建、审批、取消仍按既有指令权与责任人规则。

### 6. 保留边界

- 首版不做：自动代码同步、自动合并、完整依赖图、独立决策系统、语义差异检测；不做
  Agent 整理草稿的提案工具（本轮）；不做跨 Task 的候选项共享。若试用显示主要成本仍
  在安装配对，优先修准备路径；若交接包只增加阅读与填写负担，缩减字段而不是扩功能。
- 单活跃 Run、真人责任、候选私有、原始 Session 本地保留的既有规则不变。Hub 不新增
  模型凭据；模型调用只发生在成员 Runtime 内。
- `agreement_enabled` 的开关、确认人（责任人）、发布人（Run owner）三个角色不做合并；
  执行中改派仍按 ADR-0015（先结束活跃 Run）。

## 验证

- 机器判据覆盖：并发编辑不覆盖（409 + 重取）；启用后全部入口不得绕过绑定（含重跑/
  续跑/自动指派/指令驱动的逐入口用例与 purpose 豁免用例）；自动整理超时/断线/取消/
  迟到事件不复活终态、不重复执行业务工具；草稿与候选的私有性（接收人、其他成员、
  管理员三视角均 404/不可见）；发布不可变与证据引用校验；上游新版本不改历史 Run；
  重复确认不重复创建；下载摘要不匹配明确失败；跨任务材料只读已发布。
- 真实装配验收：真 Hub/Node/Runtime 完成「后端交付 → 前端接收 → 执行 → 真人验收」，
  证据按六原语登记（`docs/agent/handoff-loop-acceptance.md`）。
- 协议与 migration 变更随对应批次 PR 提交，按仓库纪律两名独立评审后合入；协议文档
  （03）与本 ADR 同步追加。
