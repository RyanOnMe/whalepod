# ADR-0019：连续对话工作区

- 状态：已采纳（用户批准"连续对话工作区"方案，2026-10-18）
- 范围：替代 ADR-0018 决策 2（"活跃或最近一次运行的输出成为主内容"）；ADR-0018 的其余决定（讨论独立、按需详情、候选私有、无模态遮罩）继续有效。

## 问题

ADR-0018 让"活跃或最近一次运行"的输出成为主内容，但历史指令、历史回复与所属文件仍各占一处：
指令流、运行列表与选中运行的回复面板三者并列，用户必须先选择一次运行才能读到它的回复，
而运行列表、标题、状态与活动提示又在重复表达同一件事。

执行区要回答的是"这个任务到现在发生过什么、结果是什么、产出在哪"——这是一段按时间
连续阅读的对话，不是一个需要先选中才能看输出的运行浏览器。运行列表是排障工具，不是对话本身。

## 决定

1. **执行区按 Run 为段连续展示**：历史指令、Agent 回复与所属文件卡片都留在主界面，无需先选择运行。
   段序沿用服务端运行顺序（`listRunsByTask` 的 `createdAt ASC`）；段内事件保持 `seq` 顺序，
   指令按服务端创建时间插入。现有协议没有逐条回复关联，不伪造追问与回复的一一对应。
2. **运行列表不再常驻**：每段保留"运行详情"入口；详情内可切换历史运行、查看输入快照、
   交接草稿与 Console（覆盖层）。设备、时间、版本、血缘、时长与完整状态移入详情；
   每段只保留一个简短状态。**运行行动（取消 / 继续此会话 / 重跑此 Run）也在详情里**——
   段上再放一套会一屏长出十一个「重跑此 Run」，且同一件事在两处重复（#393 全链用例实测的
   strict mode 违规）。「继续此会话」点完自动收起详情，焦点回到统一输入框。
   查看历史、打开详情、切换讨论都不改变发送目标。
3. **默认续聊是一条规则，不是每次都要重新选择**：无历史默认新执行；有活跃运行时默认追问
   （优先活跃的业务运行；只有辅助 Run 活跃时也追问它，否则默认不可发送）；
   运行结束后默认续聊最近一次业务运行（`purpose = 'business'`）。
   默认续聊锁定来源配置与执行环境，仍创建新的运行记录；来源不可续接
   （无可续会话、来源失效、责任人变化、设备离线等）时**不自动改投**——保留草稿、说明原因，
   由用户明确切换为新执行；也不跳过不可用来源去续接更早的会话。
4. **草稿记录"自动选择 / 用户明确选择"**：只有空白、未调整设置且未发送的自动草稿，
   才随运行状态更新默认模式；已输入文字或明确选择过模式/来源后，默认规则不再改写草稿。
5. **共享的分页事件读取**：会话、审批与 Console 共用同一条分页读取——每页 500 条，
   以本页最大 `seq` 作为 `after` 续读至不足一页（服务端先按受众与 `after` 过滤再分页，
   游标安全）；受众过滤造成的序号空隙不视为丢帧，重复帧按事件身份去重。
   最多并发读取 4 个运行，优先活跃运行。分页失败保留已读内容，显式呈现"不完整"与重试入口，
   不把"没读到"误报成"没有记录"。
6. **对话只有一个主滚动容器**：接近底部时跟随新内容；用户上翻后停止跟随并给出"回到最新"；
   加载更早记录保留阅读锚点；展开文件、切换详情与流式更新不抢焦点。
7. **交付物仍按 `runId` 落在对应回复之后**：候选私有（"仅你可见"）与发布确认不变；
   任务级交付抽屉保留全部可见文件；待审批卡放在对应运行段；失败原因、未知副作用警示
   与完全权限标记直接可见。

## 不做的事

- 不新增服务端 API、协议字段或数据库迁移：对话模型全部由现有指令、运行、事件与交付物派生。
- 不做跨运行的文本去重，也不伪造"这条回复对应那句追问"的关联。
- 不给历史回复增加逐条入场动画；沿用现有 React Bits 控件与动效规范，不新增依赖。

## 验证

组件判据覆盖段序/插入序、去重与相邻相同回复合并、20 段窗口与更早加载（含**窗口滑动让出并发
名额**）、>500 事件末尾回复、失效重拉走**续读游标**（不从头重读）、分页失败与重试、默认续聊与
草稿不改投、六类运行状态与取消/丢失/读取不完整（披露在段体上，不在折叠区里）；
生产装配浏览器验收覆盖连续对话、双成员权限与直播受众、候选隐私与发布确认、候选/交付抽屉、
1440/390/320 布局、历史加载锚点、上翻停止跟随与菜单/抽屉还焦。

复跑入口与逐条判据见 [docs/agent/continuous-conversation-acceptance.md](../agent/continuous-conversation-acceptance.md)
（生产验收 runner `scripts/run-conversation-acceptance.mts` + 独立判定器 123 条判据、
16 组逐条负控 + 1 条正控）。实测发现的两条边界也记在那里：设备离线由客户端闸与服务端 30s 在线
窗口双重阻断（[#394](https://github.com/RyanOnMe/whalepod/issues/394) 已收口，服务端不再建出
注定失败的 Run），成员看不到助手回复是既有受众语义。
