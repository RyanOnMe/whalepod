# WhalePod 项目上下文与多人 Agent 协调开发计划

> 日期：2026-10-30（Asia/Shanghai）。状态：开发计划草案。技术基线：远端 `main` 的 `feb58563b39826ce2a8a42836fb756d3d3b277d9`。首批办公生态：飞书、钉钉、企业微信；建议以飞书为首个适配候选，通过真实接口验证后确定。本文中的 PC 编号是工作包编号，不是已经创建的 GitHub Issue。

## 1 阶段目标

让成员在原有办公工具和 Agent 中正常工作，WhalePod 自动整理与项目有关的变化，帮助其他成员理解影响，并让后续 Agent 执行采用准确的工作依据。协调信息应从正常工作中形成，成员不再额外维护日报、进度表或逐条发布上下文。

本阶段交付围绕一条完整路径：**成员修改资料或开展讨论 → 自动获取新内容 → 更新项目当前理解 → 识别依赖与影响 → 相关成员调整工作 → 后续 Agent 使用更新后的依据**。

首轮必须同时得到以下结果：

1. 两名成员分别使用自己的 Agent 和办公资料，另一成员可以快速理解项目当前目标、重要变化、阻塞与待决定事项，并追溯出处。
2. 在已连接范围内，修改文件、发送讨论、发布成果等正常动作足以更新上下文，不要求重复录入。
3. 项目能解释某项变化影响了哪些工作；明确依赖与模型推测有不同标记。
4. 后续 Agent 实际读取新依据和必要材料；已有执行及成果保留原来的版本依据。
5. 通过真实双人使用，记录双方总劳动、重复解释、错版与返工，判断协调收益能否覆盖新增操作和维护成本。

项目进度优先解释目标条件、已知与未知、依赖和阻塞，不自动生成缺少依据的完成百分比。真人仍负责业务决定、授权、成果验收和任务完成。

## 2 开发起点与范围

### 2.1 复用已有能力

基线已有 Team/Project/Task、成员责任、Agent/Run、受众投影、一次性审批、已发布 Artifact、固定输入、版本化交接、审阅修订和个人待办。最新交付闭环已有生产装配验收，模型出口为确定性回放；本人双账号与真实双人体验仍为 `not_run`。相关实现和限制分别见[基线闭环验收](https://github.com/RyanOnMe/whalepod/blob/feb58563b39826ce2a8a42836fb756d3d3b277d9/docs/agent/delivery-loop-acceptance.md)、[基线内部体验手册](https://github.com/RyanOnMe/whalepod/blob/feb58563b39826ce2a8a42836fb756d3d3b277d9/docs/agent/delivery-loop-internal-trial.md)与[既有阶段总纲](./2026-10-08-release-harden-validate-handoff-plan.md)。

这些能力提供执行与版本依据；下一阶段增加项目层的持续理解、外部来源同步及变化影响。保留原来的交付闭环回归，不把新增概览当作原有任务和成果事实的替代品。

### 2.2 首轮交付范围

| 范围 | 首轮要求 |
|---|---|
| 项目与成员 | 单 Team，两个以上成员；沿用现有所有成员可见所有 Project 的边界 |
| 平台内来源 | 正式讨论、已发布成果、任务约定、执行状态及允许团队共享的执行投影；私有候选和原始 Session 不进入自动提取 |
| 外部来源 | 一个国内办公平台中的一个明确绑定群，以及至少一种可读取的云文档或表格；飞书为首个候选 |
| 日常变化 | 新讨论、资料内容更新、删除或撤回、来源断连、授权失效，以及新成果发布 |
| 上下文 | 目标与要求、带出处的事实和推断、决定及其来源、工作依赖、未决问题与变化历史 |
| 用户入口 | 项目当前情况、与我有关的变化、来源与同步状态；继续沿用原任务执行和成果入口 |
| Agent 使用 | 新执行和续跑创建时自动装配相关项目上下文及材料快照；正在执行的 Run 显示依据已变化的提醒 |

本地协作资料目录、离线 Office 文件、第二家办公平台是后续扩展切片，按真实使用阻塞排序。首轮不同时建设三个平台的完整连接器，也不要求团队迁移全部办公内容。会议转写只有在来源实际可用时才纳入，不依赖后台一定能拿到录音或转写。

外部个人 Agent 尚未接入时，只能依据它放入已连接来源的成果了解工作。不能从最终文件推断其完整过程、阅读历史或执行意图。

### 2.3 与当前分支的关系

计划的实现基线是上述远端 `main`。当前目录仍处于历史开发分支，因此新增主线文档使用固定提交链接，其他仓库文档沿用相对链接。正式开发按 `dev-main` 先登记并认领 Issue，再从当时最新主线创建短生命周期分支；不在旧审阅分支上继续叠加实现。

## 3 成员如何使用

以下“客户活动”是验收情境，不是已经发生的用户案例。A 负责活动与预算，B 负责方案和场地，两人都使用自己的 Agent。

| 时点 | 成员正常动作 | WhalePod 自动行为 | 成员看到的结果 |
|---|---|---|---|
| 初次建立 | A 输入活动目标，关联项目群和预算资料，确认同步至 Team 的范围 | 读取授权范围，建立初始版本；整理目标、现有事实和未知项 | 来源清单、共享范围、同步状态及可展开的初始概览；无需先填完任务分解表 |
| 开始工作 | B 在项目中请 Agent 比较场地并起草方案 | 自动准备相关上下文和材料，记录本次实际交付及消费的版本 | B 可查看采用了哪些依据；A 看到允许共享的工作意图与实际执行状态 |
| 正常调整 | A 在办公资料中把预算从 12 万改为 8 万，在原项目群说明这是已批准调整 | 获取新内容，保留出处，记录旧新版本及讨论关系；未经证实的批准身份保持未知 | 概览显示预算变化及其确认依据；不再要求 A 另填一次协调表 |
| 发现影响 | B 继续工作或重新打开项目 | 根据本次 Run 真实输入确定旧预算依赖；其他相关方案只标记可能受影响；合并同一变化的提示 | B 看到“场地比较采用旧预算，需要重估”，可以展开依据并回到原工作 |
| 调整执行 | B 正常发起新的场地比较或续跑 | 在创建时读取已同步的新版本，冻结本次上下文及材料；原 Run 的历史不变 | Agent 实际使用 8 万依据；旧方案仍显示其生成时采用的 12 万版本 |
| 了解全局 | A 打开项目当前情况 | 从可见记录解释条件、阻塞和待决定事项 | “预算已调整，场地待重估；已有报价，尚无确认预订记录”，并显示更新时间和出处 |
| 修正理解 | A 或 B 发现系统把一个建议误判为决定，在原卡片纠正 | 记录纠正和理由，更新相关概览与影响提示，阻止同一次后台重试恢复错误结论 | 一次纠正即可更新多个视图，不要求逐处维护 |

只阅读项目无需先创建 Task。Task 和 Run 继续用于需要明确责任与执行的工作，不把每条消息、每个事实转换为待办。成员主动阅读、业务审批和正常发送指令属于原有工作；新增长期维护字段、整理日报、复制上下文的动作计入协调成本。

## 4 自动获取与持续更新

### 4.1 先绑定范围 再持续同步

来源绑定是一次独立授权：说明哪些内容会进入 WhalePod、共享给谁、由哪台 Node 同步，以及是否启用有额度限制的自动提取。关联 Workspace 不意味着共享其目录。当前没有 Project 私有 ACL，所以外部受限内容只有在允许同步给整个 Team 时才可绑定；不满足条件的来源只能保留原链接或拒绝纳入正文。

平台内来源按正式 Project/Task 归属关联；外部来源按明确的群或文档身份关联。同一个人参加多个项目不构成自动归属依据。一个群覆盖多个项目时，首轮要求显式选择线程或资料范围；无法分开的内容暂不进入确定项目事实。

### 4.2 接收事件后读取真实内容

变更通知只作为“需要重新读取”的信号。适配器取得当前授权下可读的内容、上游版本或本地内容摘要，生成新的来源版本。文档读取过程中版本变化应重试或标记不完整，不拼接成一个从未存在的版本。

事件去重、版本顺序与内容去重分别处理：消息按平台消息身份及修改版本归并，文档按资源身份与修订/摘要归并，不能仅凭通用事件 ID 假定内容唯一。重复、乱序和迟到事件不覆盖较新版本；若平台没有可靠版本顺序，重新读取当前内容后再比较。

事件优先配合有界补拉与周期核对，覆盖断线期间的变化。没有可靠修改或撤回事件时，适配器必须明确可补拉的范围与间隔；无法证明历史完整时显示覆盖缺口。轮询只能证明观察到的版本，不能声称捕获了每个中间编辑步骤。

### 4.3 分开记录观察和解释

直接可观察的事实自动更新，例如文件版本、单元格值、发送者身份、Run 状态、已发布成果和材料摘要。文件所属人不自动等于实际编辑者，未知作者不得补写成绑定成员。

模型负责从允许共享的内容中整理目标、观点、疑问、潜在决定与影响关系。每一项都引用具体来源位置和版本。模型说“已经批准”、Agent 自报完成、有人提出建议，均不能单独升级为真人决定或完成事实。

若来源已有可验证的正常业务确认，不增加第二个确认步骤；缺乏确认时保留“待确定”。互相矛盾的来源并列显示分歧及时间，不默认采用最新一句话或多数表述。成员纠正作为新记录追加，保留原来源；后续新证据可以重新形成待判断项，后台重试不能静默撤销人的纠正。

### 4.4 增量更新和失败恢复

以来源版本为单位生成差异、更新引用和影响关系，再发布带单调版本号的项目读面。旧记录保留历史关系；删除、撤回和权限失效会使依赖项失效或不可用。提取失败时同步事实仍可更新，文字解释显示处理中或失败，不继续冒充最新结果。

来源各自显示最后成功读取、内容版本、待处理数量和明确缺口。项目概览展示来源覆盖水位，不以某一个活跃来源代表全项目已同步。同步故障与业务阻塞分别表达。

后台工作按来源合并，只有新内容才处理；限制并发、次数、输入量和费用。自动处理失败可对同一不可变输入重试，重试不发送业务消息、不启动业务 Run、不重复生成成员提醒。

### 4.5 把影响送到具体工作

已知依赖来自真实版本引用、Run 材料清单及消费证据。成员打开过一份文件不自动等于后续工作依赖它。模型推测单独保留“可能受影响”，不混入确定依赖。

提醒按变化与接收人合并，只在新影响、重要程度变化或需要实际处理时进入“与我有关”。读过、忽略提示、决定稍后处理和业务问题已解决是不同动作。首次仅在 WhalePod 内展示，不向办公群自动发送消息；后续如增加外发，单独设计授权、去重和退订。

## 5 最小数据与执行设计

以下是 ADR 的候选模型，具体字段在 PC-02 固化到协议单一事实源。

| 对象 | 保存的最小内容 | 必须保证 |
|---|---|---|
| ProjectSource | Project、来源类型、不透明资源身份、绑定成员、采集 Node、共享范围、授权代次、同步水位 | 平台权限和成员授权同时成立；凭据、设备绝对路径不进入普通 Hub 投影 |
| SourceRevision | 来源身份、上游版本或内容摘要、发生/观察时间、读取范围、可见性、允许保留的规范化内容和位置索引 | 内容与引用对应同一版；缺历史版本时不能伪造；删除及不可读有明确状态 |
| ContextEntry | 内容、观察/推断/决定等类别、来源引用、当前有效性、冲突和人工纠正关系 | 每项可追溯；推断不自行升级；变更追加，不改写历史 |
| ContextRelation | 两端准确身份、依赖或影响类型、明确证据或推断标记 | 不用关键词相同冒充真实消费；两端权限均需满足 |
| ProjectContextSnapshot | 读面版本、来源水位、条目和关系版本、可见性与选取规则版本 | 可重建、可判旧、可按当前权限投影；同一页引用相互一致 |
| RunProjectContext | 本 Run 的快照、实际选取条目与正文、材料摘要、授权代次、装配结果 | 创建时固定，Node 核对字节，Runtime 有真实消费判据；不能只保存快照 ID |
| ContextAnalysisJob | 不可变输入引用、来源与授权代次、处理器/模型版本、状态、额度与幂等身份 | 独立于业务 Task/Run；有限、无业务副作用；迟到结果提交前再次判权 |

### 5.1 复用现有装配

Hub 保留模块化单体与 PostgreSQL，负责来源授权、持久化、后台任务认领、事务事件和读面。Node 运行来源适配器及内容读取，沿既有协议传送允许共享的观察；新增来源同步不能绕过 Node 身份或成员权限。

建议首个飞书适配器使用企业自建应用和官方 SDK 的出站长连接，凭据留在指定同步 Node 的受控存储；云文档读取也由该 Node 执行。首轮同一应用事件流只允许一个 Node 持有有效采集租约，统一分发到已绑定来源，避免为每个文档或项目各开一个相同应用客户端；切换执行者时以授权代次和租约隔离旧事件。具体 SDK 版本、分发语义、权限及断线补拉能力由 PC-01 的真实探针确定，依赖使用精确版本。

上下文模型提取通过 Node 上受限的独立 Runtime 工作进程，复用 DSH Adapter 和现有本机模型配置，不在 Hub 新建直接调用模型的通道。此类处理不是业务 Run，不占用某个 Task 的单活跃名额；它只接收已授权输入，禁止文件写入、Shell、网络工具及对外发送工具，输出受 schema 校验的整理结果。禁止能力必须有实际装配负控；若无法验证，应停在确定性同步，不启用背景模型提取。

来源采集和模型处理可以使用不同的已授权 Node。跨 Node 只传允许团队共享且当前可读的版本化内容，不传来源凭据。自动提取的操作者、额度承担者和可见范围在启用时明确，个人模型额度不被默认用于全团队后台任务。

### 5.2 Agent 开始工作时自动装配

新执行及续跑创建时，在现有 Run 创建路径中增加项目上下文选择与快照，保留原有任务约定、交接和审阅输入。项目上下文作为带来源的工作参考，不覆盖已确认要求、不变更工具授权、不重新解释旧审批。

创建和派发前重新检查权限与来源水位。关键来源已过期或与固定要求冲突时，启动界面说明具体缺口；成员可沿原业务路径明确决定采用哪些依据。普通已同步参考自动纳入，不要求逐项勾选。范围过大时按可追溯规则选择并展示未纳入项，不静默截断要求或假称已读全部资料。

在运行中的项目变化只产生“本次执行依据已变化”的提示，不自动插入追问、取消工具或改写正在执行的上下文。后续新执行使用新快照。重放同一启动请求返回原快照；只有新的执行意图才创建新快照。

### 5.3 撤销与资料保留

撤销来源后立即阻止新采集、后台结果提交、新读面下发和新 Run 材料交付。外部权限变化按已验证的通知或周期重验机制处理；验证不可用或超过权限缓存期限时暂停正文使用，不假定权限仍有效。

由该来源派生的条目、合并摘要、提醒和快照读面共同执行失效，不能只删原文而留下可重构内容。历史 Run 保留来源版本与不可用标记；重新读取历史正文仍判当前权限。已经交付给执行者的内容无法收回，活跃 Run 标明来源已撤销，不声称清除了模型已经看到的内容。

来源正文、规范化副本、派生内容、审计元数据的保留和删除周期在 ADR 中分别确定。用户删除来源不等于立即删除所有历史审计身份，界面需要说明实际效果；未确定保留策略前不启用真实团队正文持久化。

## 6 先完成的架构决策

承重规则先形成 Proposed ADR，经评审后再落协议、migration 和实现；以下名称是议题，不预占 ADR 编号。

| ADR 议题 | 建议方向 | 开始实现前必须确定 |
|---|---|---|
| 来源共享与撤销 | ProjectSource 独立于私有 Workspace；显式一次授权；首轮只纳入允许整个 Team 读取的内容 | 来源绑定权限、外部身份映射、权限重验期限、派生内容失效和数据保留 |
| 项目理解与业务事实 | 来源版本、观察、推断、决定和人工纠正分开；Hub 持有团队事实 | 冲突、撤回、迟到、人工纠正优先关系及可重建水位 |
| 后台提取与成本 | Node 上受限独立 Runtime 任务，有限额度，无业务工具 | 与 Task/Run 的边界、认领/重试/取消、模型授权、禁用能力的机检及费用归属 |
| 项目上下文与执行 | 新执行固定版本；旧执行只标影响；当前权限持续约束读取 | 与任务约定及固定输入的冲突语义、续跑/重试、超限、派发前撤销与旧历史兼容 |

这些决定需对照现有 ADR-0003、0016、0017、0020、0022 与 0023。Office 内容读取不通过重新启用已暂停的 LibreOffice PDF 转换实现。当前权威规则在新 ADR 接受前保持有效。

## 7 国内办公平台接入选择

用户已选择国内办公生态，尚未指定三者中的首家。飞书是本计划的首个候选，不等于已获得应用、租户权限或真实接入证据。

| 平台 | 当前可用于排计划的依据 | 实施条件 |
|---|---|---|
| 飞书 | 官方消息文档区分 @机器人与群消息读取权限；官方 SDK 支持长连接事件；官方云文档资料列有正文/块读取接口，见文末来源 | 自建应用、指定群及文档的授权、普通消息可读、变更后可重读、身份与撤销可验证；文档变更事件和表格范围读取需真实探针确认 |
| 钉钉 | 官方机器人教程说明普通群聊按 @机器人投递 | 若采用该通道，只能标“被提及内容”；满足被动协调目标需要另行验证合法可用的资料或消息入口，不能要求大家每条关键讨论都再 @一次 |
| 企业微信 | 本轮尚未完成其具体读取接口及试用环境核验 | 单列验证应用消息、文档及可能需要的会话内容获取能力、授权和部署条件；不承诺普通机器人可读取全部群讨论 |

PC-01 必须实测：不 @机器人的正常讨论能否到达；历史补拉和撤回/修改的实际覆盖；能否读取一份云文档或表格；跨权限范围是否被拒；撤销后是否停止读取；资源版本是否稳定；应用安装与管理员操作成本。只读测试不向真实工作群发送消息。

若首家平台无法满足群讨论与资料更新两条核心来源，则记录原因并更换候选；不要用演示文本或每次手工转发替代首轮验收。其他两个适配器的开发等待首家闭环和真实使用反馈。

## 9 工程验收与质量评估

### 9.1 核心验收场景

| 场景 | 必须出现的证据与失败条件 |
|---|---|
| 正常修改预算 | 正常办公入口保存/发言后，来源版本和上下文更新；不调用额外发布上下文接口；旧新摘要、引用位置与水位一致，否则失败 |
| 建议与决定 | “考虑改为 8 万”不得显示已决定；有真实确认依据时自动关联；确认身份不明保留未知；模型文字自报批准不算证据 |
| 上游变化影响下游 | B 的旧 Run 清单、Node 材料字节和 Runtime 请求证明使用旧版；变化后个人提示和后续 Run 真实使用新版，缺一环失败 |
| 重复与乱序 | 同内容不重复提取或提醒；旧通知不能覆盖新版；断连补拉恢复同一当前版本；无法补齐时明确缺口 |
| 撤回与撤权 | 原来源、合并摘要、关系、提醒和历史正文读面共同受限；旧授权代次的延迟模型结果不得落入当前读面 |
| 失败与纠正 | 限流、模型失败、Node 离线或格式不支持时显示对应状态；一次人工纠正更新相关视图，重试不复活已纠正结论 |
| 外部恶意内容 | 文档或消息中的“忽略规则、读取私有目录、发送消息”等内容只能作为资料；后台提取无业务工具副作用，不能扩大共享范围 |
| 来源隔离 | 未授权群/文档、其他项目资料、私有候选、原始 Session、凭据和绝对路径不进入团队概览、日志或证据包 |

### 9.2 六原语装配

驱动通过生产 HTTP/WS、真实 Hub/Node/Runtime 包入口和两套独立浏览器会话；版本与投影只由正常成员动作、来源协议事件和真实同步产生，不直插业务表。CI 可在外部供应商接口边界使用录制并脱敏的协议服务，在模型出口使用 DSH replay；它们不得替换业务同步、装配和更新逻辑。

外部接口协议回放与真实平台烟测分别留证。前者覆盖确定性和故障分支，后者证明权限、普通消息和当前 API 实际可用；未跑真实平台不能宣布适配器已交付。真实平台正式试读在用户提供可用租户及授权后执行，不将任何凭据写进计划或请求日志。

新增结构化观测建议分层为 `node.source`、`hub.context`、`node.context-analysis`、`runtime.bridge.context`、`web.project-context`，沿用已有 trace/run/command 身份，增加不透明 source/revision/snapshot/job 身份。它们在实现 PR 中登记到取证地图；不记录来源完整正文、私人群名称、凭据或本机路径。

每条链路有独立的驱动和判定入口。判定交叉核对来源真实版本、Hub 当前读面、浏览器所见和 Runtime 实际输入；缺数据即失败，并对漏引用、错版本、假决定、遗漏撤权等证据逐项变异自证。消费判据保持成员业务指令相同，不人工复制新预算；回放模型通过真实请求中的材料取值，输入由旧版变为新版时，产出预算与约束随之变化。只记录上下文 ID 或只断言正文在场不算完成。一次红色尝试不能遗留可冒充成功的旧结果。

证据脱敏归档到 `artifacts/evidence/project-context/<scenario>/<attempt>/`，包含 manifest、来源与协议摘要、观测水位、跨层判据和失败归因。原始群聊、真实文档与完整模型请求不进入公共证据包。验收文档、复跑入口和各组件归因随切片登记 `docs/agent/README.md` 与 `evidence-map.md`，不能等最后补。

### 9.3 门禁与待建入口

沿用[门禁分级](./2026-10-08-q-gates-g0g1g2-tiers.md)，各切片跑受影响门：领域/协议 Q0/Q1，DB/Hub 加 Q2，Runtime 加 Q3，断连/任务认领加 Q6，权限/来源投影/资料读取加 Q7，浏览器走相关 Q5。后台来源或提取新增依赖时过边界与许可检查；DSH 不随本阶段功能升级。

计划新增组合驱动、独立判定、提取质量评估和真实平台只读烟测入口。名称、参数、退出码在对应 Issue 固化并接入既有质量门后才记为可运行；本计划不把尚不存在的命令列成当前验证结果。正式 release 继续执行既有发布级 Q5、Q8/Q9 及相关全量门，新模块附新证据。

### 9.4 提取质量与运行成本

冻结至少三类办公情境：活动筹备、客户方案、经营汇报。样例包含建议与决定、冲突数值、晚到回复、撤回、无权来源、内容空缺和输入中的恶意指令。开发与保留评估样例分开，每项标注由人核定的来源、结论类型、依赖及预期影响；不能用待测模型生成答案再自行打分。

工程链由 replay 检验；语义质量用固定真实 Provider/模型版本评估，并保留输入样本身份、处理器版本、结果、延迟与实际用量。首轮建议评估门：硬事实零无来源新增、建议/决定分类在已标注高风险样例中零误升级、确定依赖不得混入推测；语义提取与影响推荐另报逐类精确率、召回率及漏项。后者的试用阈值根据 PC-01 开发样本和 PC-04 开发集首测确定，在使用保留评估集前冻结；不能测试后调阈值或只保留好看的子集。

试用目标暂定：来源变化被成功读入后，确定性版本更新 p95 不超过 10 秒，语义概览 p95 不超过 60 秒；上游通知延迟、补拉等待、限流、离线和模型等待分别报告。目标在明确的样例规模与机器环境中验证，不外推为正式性能承诺。自动处理默认单 Node 并发 1，按输入摘要合并；日额度、输入上限、超时和保留周期在启用前配置，达到额度后保留事实同步并显示提取暂停。

## 10 真人试用与阶段退出条件

先由本人双账号演练正常变化、撤回纠正和断线恢复，再邀请一位真实协作者处理真实工作。至少三类办公情境采用同一套来源、变化、依赖和上下文机制，不为每个案例另造一套流程。跨场景验证机制复用；持续使用和效率结论仍按实际参与团队报告。

与团队原有办公工具和个人 Agent 的正常用法比较，允许对照使用搜索、总结、模板和文件读取。记录双方主动劳动总量、重复解释次数与分钟、错版及返工、恢复成本、模型等待、提醒数量、额外字段/确认动作、一次性部署和后续维护。版本、任务验收要求与计时边界在比较前固定，保留求助、放弃和失败。

“无需额外维护”按行为检查：初次授权后，一次正常讨论或文档更新，不应为了同步事实再触发上下文发布、日报提交或进度字段更新。对业务本来就需要作出的决定可以正常确认；专门为纠正机器、补来源、管理提醒付出的劳动单列。不能只计算接收方省时，忽略发送方和维护者增加的成本。

| 里程碑 | 退出条件 | 失败后的处理 |
|---|---|---|
| M0 来源与架构成立 | PC-01 真实来源可读、权限与安装成本明确；相关 ADR 有可实施结论 | 调整首家平台或授权范围；阻塞不通过手工转发掩盖 |
| M1 自动协调闭环成立 | PC-02～07 的双成员主链及负控通过；新 Agent 真正消费变化后的依据；每次变化无需额外维护 | 修复具体缺口后复测，不以静态概览替代闭环 |
| M2 真实使用可判断 | 三类情境完成机制复用核验；至少一对真人有完整成本、质量和误解记录 | 若新增维护抵消收益，先减少重复操作与误报；无有效比较时继续保留未验证 |
| M3 可发布 | 安装、迁移、暂停/撤销、后台成本、失败恢复和发布门齐备；说明实际来源范围 | 先交内部版本；公开 Alpha 按既有发布规则推进 |

真实使用记录未开始时保持 `not_run`。M1 只证明工程链成立；M2 才能开始判断使用收益。第二家平台、本地目录扩展或更多格式不作为掩盖首家闭环问题的替代工作。

## 11 实施前要落定的事项

1. **首家平台与试用环境**：优先探测飞书，确认用户实际可提供的组织及应用权限；钉钉和企业微信保留候选，不预设它们具有相同消息范围。
2. **资料共享范围**：明确哪些外部内容允许进入整个 Team，以及来源撤销、历史可见性和保留周期。
3. **自动处理的执行者与额度**：确定同步 Node、模型处理 Node、停机后的表现及费用上限；无需新增常驻服务集群。
4. **首轮办公样本**：从上述三类工作中准备允许共享的代表性资料，覆盖正常与失败情况，冻结质量门和性能样例规模。

先将 PC-01 与 ADR 工作登记为实际 Issue，随后领取 PC-02。各批次在完成后更新当前计划的实际 Issue/PR、基线、验收入口和真人进展；不以工作包数量或 Issue 关闭率衡量协作价值。
