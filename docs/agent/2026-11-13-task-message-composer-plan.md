# WhalePod 产品开发计划：任务页消息框与发送受阻提示

- 日期：2026-11-13。状态：第一步方案已确认，待登记与实施；本文件不记录已交付或已通过的验收结果。
- 范围：任务页底部的消息框、发送反馈和恢复入口。沿用现有两条消息路径与授权规则。
- 交给执行者：先按本文的验收表复现现状，再按 [Issue 流程](./issue-workflow.md) 登记或认领一个纵向切片。建议 Issue 标题：`P1-07：任务页明确消息接收方，支持发送受阻后继续编辑和恢复`。本文不预填 Issue 或 PR 编号。

## 1. 要解决的问题

在「无障碍活动筹备」演示里，成员想补一句现场情况，或请助手改一份方案，却要先弄清楚「Agent 执行」「第 2 次运行」「配置版本」和「指定设备」。原电脑离线时，页面连输入框也禁用了，还得打开设置才能找恢复办法。「草稿仍保留」也没说明保留的是没发出去的文字，还是助手已经产出的文件。

这一轮交付的结果：**进任务页就知道消息发给谁，正常发送不需要打开设置，发不出去也知道下一步怎么做。** 两个参与者可以各自照常留言；已授权的任务补充仍由系统承接，成员不用把同一句话再发给助手。

## 2. 页面怎么用

任务页底部提供一个固定的输入位置，上方用「发给团队」和「请助手处理」切换。首次打开普通任务链接时选「发给团队」；切换后主按钮分别显示「发给团队」和「发给助手」。两种模式沿用各自的阅读区和原有消息记录，不合并历史、不用 `@Agent` 或正文关键词判断去向。切换输入对象、点击「检查连接」或进入设置，都不会发送消息。

| 选择 | 页面怎么显示 | 用户提交后发生什么 |
|---|---|---|
| 发给团队 | 提示「团队成员可见」；输入提示「补充一条情况…」。 | 走现有讨论接口。成功后显示「已发给团队」并出现在讨论里。符合既有订阅或发现授权的留言仍进入后台协调；留言成功只代表已发给团队，不代表助手已经读过、采用或产出草稿。 |
| 请助手处理 | 显示「发给：座席方案助手」等真实名称；输入提示「想请助手做什么？」。 | 走现有助手消息接口。当前有合法的业务对话就向它补充；上一轮可以继续就接着说。用户只按一次「发给助手」，不需要选运行编号、设备或版本。 |
| 请助手处理，但还没选过可用助手 | 显示「还没为这项任务选助手」。有权限的责任人看到「选择本任务的助手」；其他成员按权限提示处理或回团队讨论。 | 由责任人明确选择。选项显示真实名称和已登记的用途说明；没有用途说明时不编造。选中只设置当前发送安排，不自动提交，也不改变任务责任人或项目设置。成功开始后，后续发送沿用该任务的现有对话。 |

例如：小周在「发给团队」下写「第二排可以留两个轮椅席位」；小林想主动交办时，切到「请助手处理」，写「请把这两个席位补到方案草稿里」。**演示这两种意图时用不同消息或分开场景**；不要让参与者为了证明自动承接，再把同一条补充主动发一次。

## 3. 默认接收方与草稿

- **有正在处理的对话：** 延续现有普通业务对话，界面显示真正的接收者；没有活跃对话时，才检查本任务最近一次普通业务对话能否接续。使用现有明确的发送意图和原服务端校验。来源不可用时，不跳到更早的对话，不自动改为发给团队或重新开始。辅助流程保留原专用入口；按 ADR-0019 已允许的辅助追问，明确提示用户正在给哪项辅助工作补充。发现生成的受限私有执行不可接续；可见的运行记录不等于可接续对象。
- **明确重新开始或首次交办：** 若已有可确认的任务助手（例如任务已明确指派、配置仍有效），展示其名称并沿用允许的配置；否则由责任人选。使用现有明确的助手与配置版本提交新请求，不能按列表顺序猜选，也不能把「选择本任务的助手」实现为「改派给 Agent」——现有改派可能立即触发执行。这里不增加项目级默认助手或持久设置。
- **两份草稿独立：** 团队留言和助手消息各有自己的未发送文字，按当前登录身份和任务隔离。在同一页面会话内切换、进出详情或去设备页返回，恢复对应的内容和已确认的发送意图。沿用现有会话内存边界；整页刷新、退出或换身份后，不承诺还在。不把未发文字放进 URL、浏览器持久存储或团队读面。
- **编辑中的消息不能被改投：** 开始写、明确选择接收对象/来源/材料，或提交等待回执后，后台变化不能改写这份意图。来源结束、责任人变化、权限撤回、资料或配置失效时，保留文字，请用户就地重新确认。发送时锁定当前文字、接收方与来源；按键或切换不能绕开校验，也不能让迟到的回执清空另一边的草稿。同一份待确认请求重试沿用原幂等键；用户改变内容或发送安排后才生成新键。

## 4. 发不出去时怎么说、怎么恢复

提示紧挨输入框，先说**发生了什么、这条消息有没有发出、下一步是谁做什么**。助手暂时不可用时允许继续编辑，只禁用相应的提交；团队留言在原有允许范围内照常可用。不同阻塞由真实原因决定，不用「未知」「服务端拒绝」代替判断。

| 可确认的情况 | 建议文案 | 就地动作 |
|---|---|---|
| 原电脑离线，旧对话在原电脑上 | 「上次用的电脑没连上，消息还没发出。你可以继续编辑。」 | 「检查连接」刷新现有状态；上线后只恢复发送按钮，不替用户发送。 |
| 旧对话已不能继续，但已确认有可用的授权环境；或原电脑离线，但有符合条件的备选 | 「你可以重新开始。你写的消息会保留，旧对话不会带过去。」若确定会换电脑，再提示「这次会用另一台已授权的电脑」。 | 「重新开始」明确切换发送安排；显示接收对象及需要重新确认的材料，最后仍由用户发送。没有已确认的可用环境时，不显示可立即重新开始的承诺。 |
| 尚未配置可用环境，或没有证据确认可用 | 对责任人：「还没有可用的电脑来处理这条消息。」状态读不到时：「暂时无法确认电脑能否使用。」 | 能检查就提供「重新检查」；确实要准备时用「设置执行电脑」，并能返回原任务和原草稿。协作者只看业务级提示，不浏览别人的设备或目录。 |
| 普通成员没有交办权限，或权限刚被撤回 | 「这项任务由小林负责交办。你仍然可以给团队留言。」 | 「发给团队」只切换到团队草稿，不复制或发布助手草稿。姓名读不到时写「任务责任人」。 |
| 等责任人接受任务或确认任务要求 | 「等小林接受这项任务」或「请先确认任务要求，再请助手处理」。 | 有权的人就地进入现有接受/确认入口；其他人看到在等谁。系统为私有草稿派生的约定不算正式确认。 |
| 发送时原安排已经变化 | 「刚才的对话已经结束，这条消息没有发到新的对话。请确认要接着说还是重新开始。」 | 根据现有来源能力提供合法选项。发现执行的私有对话不能靠这里重开或续接。 |
| 请求超时，尚不能判断是否已收到 | 「暂时没确认助手是否收到。你写的内容还在。」 | 「重新确认」或「重试发送」沿用同一请求的身份，不另起一条。只有能确认未提交/被拒时才显示「没发出」或「未受理」。 |

正常反馈同样以事实为准：团队留言「已发给团队」；助手请求已提交但尚未开始时「已提交，等助手开始」；明确排队时「已排队」；收到拒绝时写具体原因并保留对应内容。助手接口即便返回 HTTP 201，也要按业务结果区分排队、下发和拒绝，不能只看 HTTP 状态。助手确实已开始、生成草稿、草稿已分享和任务已验收是不同状态。没有与该留言对应的实际消费证据，就不显示「助手已读」；没有草稿与该来源的对应证据，也不显示「已采用」。现有页面无法证明时，本轮只说「已发给团队」。

「更多设置」保留助手配置版本、设备、工作目录及高级选项，正常路径不打开它。常规解释用「需要你批准时会提示」；**现有完全权限标识与发送前确认必须保留**，实际需要审批时写明具体动作及需要谁批准。支持人员需要的错误码和请求编号留在可展开的详情，不替代主提示。

## 5. 实施顺序与边界

以一个 Issue、一个可独立验收的 Web 改动交付，下列是同一切片内的实施顺序：

1. **先接入口和草稿。** 在 [`TaskRoomPage`](../../apps/web/src/routes/TaskRoomPage.tsx) 接入底部切换，复用 [`CommentComposer`](../../apps/web/src/features/task/CommentComposer.tsx) 和 [`ExecutionComposer`](../../apps/web/src/features/task/ExecutionComposer.tsx) 的两条提交路径。现有普通任务入口默认从团队侧开始；审批、交接、成果链接和旧讨论/执行锚点仍进入原来的相关位置。点击已发布成果里的引用、复核或修订动作，仍进入原目标，不借此重做引用、复核或成果页。
2. **再收起技术选择，补足恢复。** 在 [`ExecutionComposer`](../../apps/web/src/features/task/ExecutionComposer.tsx)、[`InstructionComposer`](../../apps/web/src/features/task/InstructionComposer.tsx)、[`RunLauncher`](../../apps/web/src/features/task/RunLauncher.tsx) 及 [`TargetPicker`](../../apps/web/src/features/task/TargetPicker.tsx) 复用现有来源和自动环境解析。把「能编辑」与「能提交」拆开，按上表接就地动作；使用 [`execution-drafts.tsx`](../../apps/web/src/features/task/execution-drafts.tsx) 所在的页面会话边界。现有团队留言重试默认会生成新键，本轮让两种草稿分别保存各自尚未确认请求的幂等键。准备检查只证明当前准备条件，不能当作模型已调用、权限已授予或未来能成功的凭据。发送时仍由 Hub 按当前责任、来源、配置、设备、权限和任务状态判定。
3. **最后补事实反馈和端到端验收。** 改掉「团队成员之间 · 不触发 Agent」这一绝对说法。显示「团队成员可见」即可；系统按已有授权接住留言的路径照常运行。不拼接两条消息流，不把普通评论转换成直接指令，不靠客户端猜测快慢路径、来源归属或草稿受众。

现有接口优先：`POST /tasks/:taskId/comments`、`POST /tasks/:taskId/instructions` 保持分开；明确的新请求继续提交实际助手与配置，追问和接续继续钉原来源。Web 不省略 `intent` 走旧客户端的隐式路由。另一台电脑是否可用、某条历史是否允许接续，只依据已有授权读面或现有准备检查；若事实不足，显示重新检查或准备入口，不用猜测填齐。若实施发现确实必须新增权限、修改状态机/协议或改变默认执行授权，先另立 ADR；不得为了少一个按钮扩大读面或放宽守卫。

本计划更新 [ADR-0018](../adr/0018-focused-task-workspace.md) 的任务页默认展示与输入入口取舍。执行 PR 同步记录这两处变化；[ADR-0010](../adr/0010-discussion-execution-separation.md) 的讨论/指令隔离、[ADR-0013](../adr/0013-explicit-execution-intent.md) 的发送意图和 [ADR-0019](../adr/0019-continuous-conversation-workspace.md) 的草稿与接续规则继续有效。旧文档中的「讨论不触发」应理解为不把评论当作直接指令；[ADR-0028](../adr/0028-continuous-work-and-autonomous-dispatch.md) 与 [ADR-0030](../adr/0030-project-work-discovery-and-creation.md) 所允许的后台承接不变。

这一轮不改项目首页、任务创建、成果页、引用方式、项目级助手配置、Router 判断、派工、计费或外部接入。资料授权、私有草稿可见范围、正式发布与验收沿用现有规则。飞书仍等测试租户授权，正式阅稿不启用。

## 6. 验收与交接

以「更新场地无障碍座席方案」为例，用测试环境从正常页面操作。准备责任人和另一名成员、可用的助手和合法环境，以及启用订阅的既有任务；准备和授权动作单独记账。模型可用确定性回放，提交、读取权限和反馈走真实装配。至少覆盖以下结果：

| 场景 | 必须有的证据 |
|---|---|
| 正常补充 | 普通链接进入时默认「发给团队」。发一条现场补充，只产生一条团队评论、零条直接指令；既有订阅仍接收该评论。要声称已采用，按同一来源身份核对后续读取/消费回执，不能拿留言 HTTP 成功代替。 |
| 主动交办与首次选择 | 正常接续时能看到真实接收者，不打开设置即可发送；请求命中已展示的来源。没有可沿用的助手时先由责任人选择；选助手本身零次提交、零次改派。发送后只产生一次预期的交办。 |
| 双草稿及请求结果 | 切换、返回、拒绝和状态刷新不串文字、不丢当前草稿。成功只清对应草稿；迟到回执不改另一边。同一未确认请求重试不重复留言或交办；已确定拒绝不能显示已送达。 |
| 离线、恢复、重新开始 | 原电脑离线时助手输入仍可编辑、提交被阻止、团队留言正常；重新检查及上线均不会自动提交。有合法备选时，明确重新开始后才可发送，实际请求不带旧对话来源；无合法备选时不提供立即开始。 |
| 权限与状态竞态 | 没权限或刚被撤权的成员不能交办、看不到别人的环境及私有草稿；在编辑中旧来源结束、责任人变化或来源失效，草稿不改投；受限私有执行不被当作可接续会话。保留完全权限确认和原有工具审批。 |
| 原有入口可达 | 旧的讨论、审批、交接和成果锚点继续落到对应位置；键盘可切换接收对象、识别发送受阻原因并到达恢复动作；窄屏不把关键操作挤出输入区。 |

工程交付跑 `pnpm check`，并按影响运行 Q5。可从以下现有入口复用用例或装配：

```bash
pnpm exec vitest run --project web apps/web/tests/task-room.spec.tsx apps/web/tests/execution-composer.spec.tsx apps/web/tests/instruction-composer.spec.tsx
pnpm exec playwright test --project=p1-07
pnpm exec tsx scripts/run-conversation-acceptance.mts
```

生产浏览器用例至少保留一条「离线 → 继续编辑 → 重新连上 → 等人点发送」负向断言和一条「普通成员试图交办/读取私有结果」负向断言。若改到 Hub 或 HTTP 契约，再按变更范围补 Q2 和相应评审。记录本次提交、角色、消息/来源身份、回执状态与计数，不收集真实正文、设备路径或凭据；缺少关键事实不判通过。按 [验收模板](./acceptance-template.md) 写复跑记录，更新 [证据地图](./evidence-map.md) 和 [索引](./README.md)。已有 [快慢路径工程验收](./2026-11-12-rd05a-combined-paths-acceptance.md) 可作对照，不能替这次浏览器验收。

**真人验收单独记录。** 找至少一位没看过演示的成员，不介绍 Run、Agent 版本或设备设置。让他先补充座席情况，再为一件不同的事请助手处理，最后遇到一次电脑离线。观察他是否能在不打开「更多设置」、不接受口头指引的情况下，自己说出「发给了谁、有没有发出去、接下来点哪里」。记录误投、重复交办、是否丢字及是否需要他人帮助；未做时写 `not_run`，不把自动化通过当作好用或提效。

执行者交回：Issue/PR、改动范围、真实复跑命令和结果、两种接收对象及离线状态的演示证据，以及未完成的真人验收。产品层面的后续顺序是先让发送路径通过试用，再改文件引用和成果页。
