# WhalePod Router 与 Executor 持续协作方案

> 日期：2026-11-02（Asia/Shanghai）。状态：讨论稿。用户已确认首轮默认边界：自动研究、分析和产出草稿；正式发布、外发与业务承诺由人决定。技术基线：`main@93f41e9`（RD-02b 分支在此后开发）。本文细化[阶段计划](./2026-10-30-project-context-coordination-plan.md)的新增方向；双路径承接、派工、上下文交付与权限决定由 [ADR-0028](../adr/0028-continuous-work-and-autonomous-dispatch.md)（已采纳 2026-11-02，#480）约束；RD-01、RD-02a-1、RD-02a-2a、RD-02a-2b（Node 下载与消费回执）与 RD-02b 订阅半边已交付（WorkLink 未实现，归 PC-03b）；PC-05b-1（#498）已交付 Run 上下文撤权状态机与状态同步，PC-05b-2/-3（回执 watchdog/恢复、终态 session 清理与 `resumeContext`）仍在队列；RD-03 尚未实现，按后续切片启用。ADR-0028 只覆盖既有 Task/订阅之上的基础链；自动新建 Task/约定/新工作与同一活跃 Run 动态输入不在其范围，须另立 ADR。

## 1 产品主线：从日常工作中持续承接

成员一次确认项目目标、持续职责、可接入的资料与执行环境，以及费用和成果边界。此后照常在办公工具中讨论、修改资料和处理业务，Router 从跨成员的工作环境恢复意图，自动补齐上下文；已有工作继续承接，新缺口在授权内由合适 Agent 接手。成员不必把每次变化重新整理成执行提示词，也不必逐变化配置“当 X 发生就做 Y”的触发器。

目标是**减少临时提示词、上下文搬运与重复解释**。项目目标、重要取舍和业务决定仍需要人表达；系统负责把这些自然表达与已有工作联系起来。没有必要的消息静默处理，需要人决定时才提出一个具体问题。

首轮可自动研究、检索已授权资料、分析、核算、比较、生成及修订草稿。正式发布或覆盖正式材料、对外发送、业务承诺与最终业务验收由人决定；Run 成功不等于 Task 已验收。

持续职责和资源边界是产品中的少量默认选择，不是要求成员填写完整工作流或复杂配置表。系统应从项目材料、正常业务记录、Agent 配置与实际验证结果生成候选范围，再让成员确认摘要；内部仍需保存可机器判定、可撤销的授权。用户确认产品默认范围，不等于已授权任意项目、设备、资料或费用。

## 2 成员的日常使用

初次确认可以是：

> 跟进这个客户活动，持续检查方案是否符合已确认要求，主动补做必要研究、核算和草稿修订。使用这些项目资料和我的执行环境，在约定额度内处理；正式发布、外发及对客户或供应商作承诺时找我。

成员不用预先列出预算、人数、无障碍、交通、日程等全部变化类型，也不用为每个新缺口再写一套触发规则。Router 根据持续目标、职责和当前工作理解具体变化；新工作仍需落在已确认的职责与资源范围内。

一个客户活动场景：方案 Agent 已在准备活动方案。A 在原项目群补充“客户确认有轮椅使用者”，没有 @Agent；已有合法订阅把这条补充送到承接方案的工作，Executor 自动取得出处及相关场地资料，继续检查和修订草稿。随后 B 在正常讨论中说明“高铁站到场地交通不方便”，项目尚无接驳安排；Router 补读相关讨论和行程，在授权内识别新的工作缺口，选择合适 Agent 研究接驳并产出草稿。

已有工作无需重派，新工作也不要求人先建 Task、复制上下文或补发一句“请研究接驳”。Router 可以自动形成内部工作记录和可验收简报；正式发布、确认供应商或承诺费用时，才请业务责任人决定。

“如果客户有轮椅使用者”与已确认要求必须区分。系统可将假设保留为参考，不自行升级为决定，不为了每条闲聊或方向未定的讨论追问人。缺少上下文时先自动读取有权读取的关联信息；读取后仍有真实业务取舍，或授权、资源及恢复路径无法覆盖时，再转人工。

以上是完整目标。现有 Task 首切只是工程过渡，不能把“人已建好 Task、确认好逐项工作、重写执行提示词”作为完整产品成立的前提。

## 3 两处快慢路径

快慢分流既发生在入口，也发生在工作承接。快路径减少重复判断、无效推理和人的等待；慢路径用于真正需要理解和重新协调的情况。

### 3.1 入口：程序准入与必要语义判断

程序先按可验证信息处理监听范围、当前读取权限、重复事件、来源版本、已知订阅和系统自身产生的普通状态。已确定的重复、无权或无需唤醒的内容直接静默处理，不为每条消息调用模型。

需要理解的新信息再进入有界语义判断。模型从跨成员讨论、项目目标、现有成果和工作记录中恢复意图，自动读取必要的父消息、相关线程和资料片段。程序无法确定“无关”时不能只靠关键词丢弃；模型也不能仅因出现命令语气就取得执行权。材料中的指令和假设仍按资料处理。

### 3.2 承接：已有订阅直达工作，新缺口再经 Router

已订阅线程、资料或业务事件中，属于同一持续职责且权限仍有效的补充，按稳定工作身份进入承接工作的收件箱。无需中心 Router 模型逐条重新派工，成员也无需再次 @Agent、转发或写提示词。Executor 可在自己的工作上下文中理解补充；直达不等于绕过入口准入、资源权限或预算。

没有承接者、出现新缺口、目标冲突，或 Executor 发现超出原职责时，再进入 Router 慢路径。Router 查已有工作、补上下文、判断缺口是否已被覆盖，并决定派工、等待、转人工或忽略。无法处理的补充应带原因退回，不能悄悄丢弃或由 Executor 自行越权扩展工作。

```text
日常消息、资料与业务变化
  → 程序准入、去重与版本判断
  → 已有合法订阅：持续工作收件箱 → Executor 承接 → 状态与合格结果回流
  → 新工作或超范围：Router 补上下文与判断 → 授权裁决 → 合适工作/Executor
```

完整目标包含持续订阅承接。现有生产协议尚未支持的活跃上下文交付不能写成现成能力，也不能用“先结束、再由人重发一条指令”替代长期产品目标；其工程过渡和完整验收分别见 §8。

## 4 持续工作身份、收件箱与运行

### 4.1 工作持续存在，Run 是一次执行

用稳定 `workKey` 标识同一项目职责下的一份持续工作；它关联目标、承接者、订阅、输入水位、未决问题和成果，可以跨多个 Run 延续。Task 继续承担责任与业务记录权威；`workKey` 是关联和交付身份，不另设一套业务工单状态机，也不等于 Task、Session、一次事件或一次 Run。两个独立同类工作不能因为名称相似而合并。

`inputDigest` 单独标识本次选入依据。重复通知和同版本重读不产生第二份工作；新版本只改变待处理输入。工作结束也不复活旧 Run。已完成或取消的 Task 不直接重开；新缺口在完整阶段由新的工作意图及获准的约定模板形成新业务记录。

### 4.2 收件箱负责可靠承接

工作收件箱保存待处理事件身份、出处及版本、当前授权引用、因果关系和处理状态。Node 离线、排队或模型忙时，内容仍保持待交付；恢复后幂等补送，不让成员重新复制。重复到达、跨入口重读和同版补拉归并为同一输入；合并只压缩重复与可替代的状态变化，不丢失独立要求、人的纠正或尚未处理的问题。

交付状态至少区分：进入工作收件箱、交付到指定 Executor/Run、在明确执行边界被实际消费、被拒绝或退回。消费回执绑定准确输入身份、版本、水位、Executor/Run 与时间，不能把 WebSocket 已发送、工具返回成功或 Agent 自称“看过”当作全部内容已消费。回执和正文读取有真实装配判据；缺回执明确显示未确认，恢复机制不能读取旧成功结果充数。

已订阅内容也可能不属于当前工作。Executor 退回时说明无关、新缺口、冲突、权限失效或输入不完整，并保留已消费水位；Router 对同一退回去重，必要时补上下文重新选择承接者。转交不扩大资料受众，Executor 不能自行把私有内容传给其他成员或 Agent。

### 4.3 保留现有 Run 约束，扩展交付边界

Task 单活跃 Run、Run 终态不可复活、创建时固定输入和原有审批仍有效。拟议工作收件箱不伪装人类 `run.followup`，不改写 Run 原始快照，不把资料更新当作停止或扩权指令。

已有 Task 的 A 切片可先把活跃期间的变化留在收件箱，Run 终态后复核：成果是否已覆盖变化、授权和 Task 是否仍有效、最新输入是否需要执行，再建立新 Run。不能因积累了一条通知就必起下一轮；这只证明安全的工程过渡，不代表持续承接目标已经完成。

M1R-B 可在 Run 边界自动续接，合并待处理变化后建立新 Run、固定新依据并精确记录消费；配合新缺口自主承接，即可验证完整主链，无需先支持同一活跃 Run 动态接收。若后来开放同一 Run 的增量上下文，再单列新 ADR：明确安全消费步骤、初始快照与每次追加引用的关系、当前权限和逐项回执。当前 Run 无法接收时收件箱持续保管，直到合法边界消费，不静默丢失。自动停止正常业务执行或把补充升级为新指令，仍需各自授权，不能由“订阅”推导。

## 5 Router 决策与 Agent 选择

### 5.1 四类决定

候选工作由环境中的目标、讨论、资料和现有工作形成。Router 应自动整理“为什么现在做、已有工作为何未覆盖、依据与约束、期望成果和验收方式”，不要求人先填写工作简报。优先处理已有承诺受影响、阻塞下游或临近截止的缺口；可有可无的改进不自动挤占预算。

| 决定 | 适用情况 | 产品行为 |
|---|---|---|
| dispatch 派工/承接 | 职责明确、依据可用、尚未覆盖，且通过授权、Agent、现场及费用校验 | 自动形成可追溯工作意图，关联已有工作或新建合格工作，再经统一执行入口派发 |
| wait 等待 | 等待上游、同一工作正在运行、Task 单活跃、暂时离线、短期限流或容量不足 | 收件箱可靠保留，订阅状态变化，按期限重评；不反复请求人点确认 |
| ask 转人工 | 补上下文后仍有真实业务冲突、目标取舍、必要扩权、无合格候选或无法恢复 | 向正确责任人提出一个有出处和推荐选项的问题 |
| ignore 静默 | 无关、重复、普通自报状态、假设尚不构成工作，或没有需要行动的缺口 | 留最小原因和必要上下文；不建多余工作、不发确认、不制造提示词任务 |

模型提出工作与路由，Hub 的确定性策略裁决能否派发。模型自报置信度和 schema 合法不替代授权；涉嫌越权的材料先按策略拒绝，不包装成邀请人扩权的问题。

### 5.2 先合法，再比较适合程度

1. **硬筛**：当前授权允许的 Agent/Profile Revision、资料与工具、成果受众、真人责任人、Node/Workspace、凭据及费用同时满足；已归档或不合格候选不参加排序。
2. **连续性与能力证据**：已有承接 Agent 优先，在满足工作要求后，再比较已验证同类经验、格式/工具适配、完成时间和成本。等价候选按稳定规则选，不逐次请人点名。
3. **即时准备**：核对摘要、在线状态、Workspace、凭据和容量。现有准备检查不证明真实模型质量或价格，绿色状态不是能力保证。
4. **派发前复核**：固定 Agent/Revision、授权版本、责任人/现场、输入身份与预算。等待中权限、资料或配置变化后重新评估，不静默改目标。

能力描述优先从 Profile、插件、工具和验证记录生成，补少量用途及不适用场景。角色人设和自称“擅长财务”不等于质量证据，不引入无数据依据的能力分数。在线的文案 Agent 不能仅因原分析 Agent 离线就代替核算。

Agent 角色与执行现场分别选择。团队 Agent 不授予其他成员设备或凭据的使用权；现有目标解析仅允许 Task 责任人名下现场，后台 Router 需要新的授权接缝，不能冒充真人调用准备或指令接口。替换只选已授权合格候选，并保留交接与新执行身份；resume 不自动换 Agent、设备或 Workspace。

## 6 一次确认的持续职责与人的介入

持续授权（Mandate）由项目目标、默认职责及必要边界形成。界面以自然职责、可读默认与摘要确认呈现；以下是内部必须表达的契约，不是要求每位成员逐项填表。

| 契约范围 | 内部需要明确 |
|---|---|
| 主体与职责 | 谁授权、代谁行动、真人责任人、项目目标、职责范围、有效期和版本；不代另一成员承担责任或费用 |
| 资料与执行资源 | 可读来源、可用 Agent/Revision、模型、现场、凭据与工具；拥有者许可独立成立 |
| 工作与成果 | 自动研究/分析/草稿、允许新缺口及工作深度、可验收职责/模板、草稿区域与受众；正式发布/外发/业务承诺由人决定 |
| 总上限与停止 | Router、Executor、复核、转交与重试共用次数/费用上限，等待/截止期限、暂停及撤销；拆任务不重置预算 |

授权在决定提交、派发前及相关工具执行时复核。撤销、到期或硬额度触发后阻止未派工作与新增动作，由宿主取消并收敛在途派生 Run；具体竞态由新 ADR 固化。已发生动作先核对结果，不承诺收回。

Executor 接收工作目标、固定依据、授权动作和输出约束。已预授权且可机器验证的低风险工具步骤直接执行，超出许可交现有审批人；启动授权与工具许可分开，不能用 `full_access` 解决自主性，也不能自动启动后每一步仍强迫人点击。文件只写指定草稿区域；无法验证工具/路径限制的组合不成为自主候选，Router 不自己批准动作。

草稿默认交给授权责任人，沿用现有私有 Artifact 候选范围。项目可见状态和获准摘要；Router 或另一 Agent 不因协调职责获得私有正文。首个执行切片限同责任人授权现场；多 Agent 中间产物需要明确受众、委托读取和受控交付，不借正式发布路径绕过人的发布决定。Executor 可在授权私有现场做可机器检查的核验并回传合格摘要；自报质量不等于业务验收。

| 情形 | 自动处理或介入对象 |
|---|---|
| 已承接职责内的补充 | 快路径可靠交付，Executor 自动取上下文续接；不要求人重发指令 |
| 授权内新研究、分析或草稿缺口 | Router 补上下文并选择合格 Agent，自动形成工作记录和简报 |
| 排队、上游未就绪、暂时离线或限流 | 等待或安全重试，达到期限/上限才升级 |
| 已确认要求冲突、目标取舍或业务承诺 | 业务责任人看出处、选项和推荐后决定 |
| 扩权、其他成员现场或增加费用 | 对应授权人和资源/费用拥有者，不一律交管理员 |
| 正式发布或外发 | 业务责任人决定并走正式入口，不随草稿就绪自动发生 |
| 连续不合格、无合格 Agent 或预算耗尽 | 停止新增尝试，提出调整范围/资源/等待的选择 |
| 失败可能已有副作用 | 先核对真实结果，无法判断再找人，不换 Agent 重放 |

人工问题按同一决定合并；只有回答的主体、授权和语义适用于相关工作，才一次解除这些阻塞。业务决定、已读、草稿就绪和正式验收分开。普通消息不需要人确认一次，人的一句话也不自动被解释为所有工作的批准。

派工/承接记录至少保存：触发与来源版本、稳定工作身份、快/慢路径及原因、Router 决定、候选及排除理由、选中 Agent/Revision、当前授权、真人责任人/现场、输入身份、预算、交付/消费状态及实际 Run。记录系统 actor 和所代表成员，不伪造成员会话；不另要求人维护路由台账。

## 7 与已采纳架构的衔接

PC-03a 事实账本、PC-04a 确定性协调和 PC-05a 正向快照与消费是基础，尚不包含本方案的持续工作订阅、自主承接或模型 Router。已采纳 ADR-0026 仍禁止协调计算直接创建业务 Run；新方向先形成独立 Proposed ADR，采纳后按切片实施，不能把讨论稿写成现成能力。

| 现有约束 | 拟议扩展或保留 |
|---|---|
| ADR-0013 明确执行意图 | 有效持续职责生成可追溯机器意图；工作上下文输入与人类指令分通道；仍复用统一 Run 入口 |
| ADR-0015 撤销与排队 | 承接、派发、重试及消费回执与撤销竞态一起裁决；失效输入不再重投，已发生副作用不伪造撤回 |
| ADR-0016 固定材料 | 保留既有快照与版本；工作订阅不静默换 Artifact。采用新版材料需新 ADR 明确的受限职责参数与采用语义，否则沿原确认路径 |
| ADR-0017 真人确认约定 | A 切片复用已有 Task 有效约定；完整阶段由真人预授权的持续职责和可验收模板承接新缺口，后台生成 Task/约定时保留真实授权来源，不伪造真人确认或关闭约定开关 |
| ADR-0025 事实与推断 | 新工作提案/派工记录不变成人工业务 Decision；工作关联、订阅与精确来源引用接受确定性裁决 |
| ADR-0026 受限协调计算 | 模型输出结构化提案；Hub 新增授权裁决的承接/派工端口，模型不直接写业务表；快路径不因存在 Router 就反复调用中心模型 |
| ADR-0027 固定输入与消费 | 保留基线，扩展有界工作上下文、可靠交付和精确消费；活跃接收与跨 Run 承接须新协议及负控，不伪装现成 `followup` |

现有 Task 首切只用于复用责任、约定、现场和执行设施，完整目标是让环境中的新工作缺口自动被承接。不能把每个新缺口都退回“请先建 Task、写提示词、搬上下文”后再宣布自主协调完成。

## 8 工作包、里程碑与验收

以下 RD 编号是拟议工作包，尚未登记为 GitHub Issue。默认产品范围已确认，具体协议和权限契约仍需新 ADR；完整快速承接也未由现有生产协议提供。

| 工作包 | 可见结果 | 退出条件与依赖 |
|---|---|---|
| RD-01 目标职责与双路径准入 | 一次确认自然职责和少量默认；日常讨论能恢复意图，无逐事件触发器配置 | 新 ADR 明确持续职责、快慢分流、机器工作意图、成本/受众/撤销及最小转人工；影子模式不建业务 Run |
| RD-02 持续工作订阅与事件承接 | 已承接消息进入工作收件箱；合法 Agent/现场匹配、交付、等待和退回可解释 | 依赖 RD-01；稳定工作身份、可靠待发、去重、消费回执协议、退回与噪声负控；角色/现场分离，能力证据不等于绿色准备；真实自动消费与 RD-03 联验，单有协议试验不算完成续接 |
| RD-03 授权内自主草稿执行 | 研究/分析/草稿自动执行；已有 Task 是 A 切片，完整订阅承接按新协议逐步启用 | 依赖 RD-01/02；A 切片 Task 已接受、非终态、无活跃 Run 且约定有效；模型/工具/路径限制、幂等、草稿、最小提问/暂停/撤销及回答后重验可用；PC-05b 撤权/回执恢复/清理补齐后才启用真实执行 |
| RD-04 新工作自动承接与人工协同 | 新缺口自动补上下文、形成合格工作并选 Executor；真正取舍才问人 | 依赖 RD-01/02 及 RD-03 的安全执行；预授权职责/可验收模板形成真实约定，不要求人手建每个 Task；持续订阅按协议续接，超范围准确退回；私有草稿和受众仍受限 |
| RD-05 快慢路径组合与真人试用 | 已知补充自动续接，新缺口自动承接；双方少写临时提示词、少搬上下文 | 依赖相关 RD 执行/承接与人工路径；程序快路径、订阅快路径、语义慢路径、真实模型及双方成本分别留证；真实外部办公仍需 PC-01/02b/03b/03c |

里程碑分开判断：

| 里程碑 | 退出条件 | 结论边界 |
|---|---|---|
| M1R-A 已有 Task 工程过渡 | 有效职责内的变化可在已有合法 Task 形成私有草稿；无重复派工确认，消费、去重、撤权、恢复与工具边界通过 | 不证明活跃订阅续接、新缺口自主承接或“无需手建 Task”的完整体验 |
| M1R-B 快慢路径持续协作 | 双处快慢路径、持续工作收件箱及自动上下文承接成立；新增缺口在职责内自动形成工作并执行；业务取舍及无法自动恢复的异常才找人 | 包含已承接订阅续接与新工作自动承接；可在 Run 边界完成，不以同 Run 动态输入为前置，不能用 M1R-A、静态概览或仅接收回执替代 |

核心场景与判据：

1. **轮椅需求续接原方案**：原工作已承接场地方案，A 在原群正常补充已确认无障碍需求，不 @Agent。程序准入后合法订阅直达该工作；Executor 自动取得出处和相关资料，在允许边界续接，精确记录消费并产出私有草稿。已知职责内补充不多跑一次中心 Router 语义判断。可在当前 Run 结束后自动开下一 Run；只有收件箱等待、没有真实续接时不报通过，和新工作场景一起成立才计 M1R-B。
2. **接驳缺口自动承接**：B 正常讨论已确认的交通困难，原方案没有接驳安排。Router 从跨成员环境补读依据、识别未覆盖职责并选合格 Executor，自动形成合格工作和草稿。初次只确认过项目目标/持续职责，无需为“交通变化”配新规则、补发执行提示词、搬材料或手建新 Task；新约定保留真实预授权来源。
3. **无关、假设、重复和进行中**：闲聊、普通状态、未确认假设与重复通知不额外派工或追问；假设不升级决定。运行中变化不改旧快照，独立要求不因合并丢失；普通结果不触发 Router/Executor 自激循环。无变化不轮询模型。
4. **退回、等待与真正转人工**：分别验证无关输入由承接者带原因退回、新缺口重新路由、临时离线可靠等待、权限或版本变化重验；已确认要求冲突、业务取舍、正式发布/外发/承诺才按正确主体提问。无合格候选、失败或额度耗尽在无法自动恢复时升级，不由多个 Agent 重复询问。

验收从成员行为检查：项目目标和初始职责可以正常表达；一次设置后的上述事件不增加 @Agent、执行提示词、上下文复制、逐事件规则或手工新 Task。必要业务决定、初次授权和正式发布另计；系统纠正、求助、等待、失误及维护成本都记录，不能把这些劳动藏在“零提示词”口号里。

机器证据区分入口准入、订阅匹配、是否调用 Router、工作收件箱、Node 实际交付、Executor 消费、退回和成果，逐环缺数据即失败。重复/乱序、断线与回执丢失、跨工作错投、旧代次重投、派发撤销竞态、预算/深度耗尽、未知副作用、跨成员草稿和资源越权必须判红。沿生产 HTTP/WS、PostgreSQL、Node/Runtime 和独立判定取证；回放验工程，真实模型验语义与路由质量，真人对照验重复提示词、搬运、额外维护和打扰是否减少，三者分别报告。
