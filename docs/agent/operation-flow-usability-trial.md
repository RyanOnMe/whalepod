## 背景与本轮问题

WhalePod 面向3–10人小团队，共享任务、讨论、运行记录和已发布产出。任务的责任人、实际执行的成员、使用的环境、审批人并非总是同一个人。每次执行是一条独立记录；继续已有会话与开始新记录有不同含义。产出先是拥有者的私有候选，确认发布后团队可见；提交验收与真人完成任务是两步。前三批已补清楚这些边界和恢复入口。

第四批在原项目首页加一个小的“需要我处理”区域，依当前用户权限显示：接受任务、重新指派、处理审批、检查候选、确认完成。点事项只定位到任务内对应区域，实际变更仍需要真人操作。候选名称、数量、工具参数和环境路径不在个人待办投影中；别人看不到候选存在的私有线索。环境配置失败仍在原任务准备界面解释，不从失败记录猜测首页阻塞。

需要回答：相比最近任务入口，第四批是否帮助用户更快找到真正需要自己处理的事？用户是否仍会误解谁执行、用谁的环境、谁审批、哪些产出已共享，以及何时算完成？现在还没有理由扩大成完整工作台。

## 四条情境任务（主持人脚本）

1. **创建与首次执行**。先给参与者一个空白项目，让他**自己建一个任务**（说：“把这件事记成任务；谁来做、什么时候开始执行由你定。”），记录他是否理解「责任人」与「创建后立即执行」是两件事、分给别人时是否知道对方要先接受；再准备一个分给参与者的待接受任务和可用设备，说：“你接到一个要交付初稿的任务，请开始处理，运行前说出谁会执行、用谁的环境、谁处理工具请求。”记录接受/准备/发起是否找到，是否错误地把讨论当执行，以及安装等待和导航耗时。
2. **继续还是另开**。准备一条已结束、有上下文的执行记录。说：“保留之前思路补充一段内容；再比较另一条独立方案。”先让用户解释两个目标的差异，再操作。记录来源是否选对、Agent和环境是否理解、输入草稿是否丢失、是否在未知来源下误发。
3. **授权协作与审批**。责任人授权另一个成员发起指令；准备责任人的设备、Workspace与凭据，协作者只需网页登录。执行固定使用责任人的现场，审批也仍归责任人。说：“请协作者执行一次补充工作，然后由应该处理的人决定待确认的工具操作。”让双方分别陈述执行者、责任人、环境归属和审批归属；观察非拥有者是否误以为能审批。另准备一次拒绝指派，由管理员恢复，记录是否找到入口、是否知道新责任人仍需接受。
4. **交付闭环**。准备已有私有候选的任务。说：“请检查产出，决定何时交给团队，再请团队查看并完成验收。若复核意见需要修订，请回到产出会话处理。”记录是否预览后发布、观察者在发布前是否知道候选、是否误把运行结束当任务完成、是否在提交验收后明确由真人确认完成。复核分支只在参与者确有修订需要时计入，不强迫触发。

每一轮另用中性问题：“现在有哪些事需要你处理？请找出一个并说明为什么由你处理。”从首页开始计时。不要把五种事项名称直接读给用户。两轮实际可用事项保持等价，记录准备的事项类型与数量。

## 本轮新增观察重点（2026-10-16）

第四/五批合入后，试用要额外盯这五处（都在上面四条情境里出现，不必新增情境）：

1. **责任与执行时机**：创建任务时，参与者是否理解「责任人」与「创建后执行」是两件事——默认只创建、要执行得显式开启；分给别人时是否知道对方要先接受、由对方安排执行（#344）。
2. **准备中断后返回**：环境没准备好时的返回路径（情境 1 与第五批补充），是否找回原任务、原文字与设置是否还在、是否把「返回」当成「已发送」。
3. **授权与审批**：执行者、责任人、环境归属、审批归属四件事参与者能否分别讲清（情境 3）。
4. **交付验收**：运行结束 ≠ 任务完成；发布与真人确认完成是两步（情境 4）。
5. **个人待办的查找表现**：从首页「需要我处理」找一件事并说明为什么归自己（每轮的中性问题）。

**记时口径（必须分开记，不合成一个数）**：界面寻找/定位耗时、执行与模型等待、安装与设备
等待三类分开记录（模板字段已分列）；**模型等待与界面寻找时间不得合并成「提效百分比」**。
执行时机相关的误判（把创建当执行、把返回当发送）单独记发生次数与原始话术。

## 记录与判定

使用同目录operation-flow-trial-template.json复制一份。参与者只用代号；每条观察记录版本、顺序、情境、事项类型、定位耗时、操作耗时、模型/设备等待、安装配置耗时、理解判断、求助、误操作、阻塞原因及脱敏原话。未观察到填null，不填0。不要记录账号、Token、会话cookie、设备绝对路径、原始工具参数或私有产出正文。征得同意后再录屏，原始录屏不进入仓库或团队投影。

独立完成：在无主持人路径提示的情况下找到正确对象，正确说明权限/环境归属，执行与目标一致的操作。报告按团队与参与者配对呈现，保留失败和求助；定位时间与执行/模型等待分开比较，不合成一个“提效百分比”。样本少时只报告分布、原话和反复出现的问题，不声称统计普遍性。

发布前置条件：机器验收与隐私负向用例全部通过。试用后若同类问题跨至少2个团队重复出现，优先修该具体路径；只有反复出现跨任务协调负担且现有入口仍无法支持时，再提出完整工作台方案。该“2个团队”是本轮决策规则，不是效果证据。若仅单队出现，保留观察并复测，不凭一次抱怨扩大产品。
