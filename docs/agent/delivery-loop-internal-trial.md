# WhalePod 交付闭环内部体验手册（#442）

状态：**not_run**。本手册没有真人结果、节省时间或效率提升结论。先由项目本人使用两个账号检查操作闭环，再邀请一位真实协作者比较双方的劳动；自动测试与模型回放只证明其覆盖的工程路径。

## 本轮要回答什么

一个人借助 Agent 产出成果，另一个人要审阅或据此继续工作时，WhalePod 是否减少了找版本、拼材料、解释修改意见和确认责任的劳动？这些收益能否覆盖发送方新增的整理、发布、选意见和检查操作？

先只体验这条路径：**成果与依据 → 针对准确版本批注 → 固定本轮意见 → 明确启动 Agent 修订 → 显式关联并发布新版 → 真人逐条复核**。对跨任务继续工作的场景，再走已发布交接版本、接收理解和下游执行输入。

## 本轮源码内部候选的使用方式

当前候选分支是 `feat/p1-442-delivery-acceptance`，包含修订闭环、成果依据和 Office 安全回退，尚未进入正式发布版。`v0.1.0-alpha.9` 不包含这些新增入口。

使用独立的内部实例，Hub/Web 与执行成员 Node 必须来自同一候选分支。沿用 [安装与恢复指引](../installation.md) 的 A/B 步骤，但将其中两个锁定 alpha.9 的 checkout 替换为当前候选分支，再从源码构建；不要升级现有团队实例来做第一轮演练。凭据仍只在执行成员本机配置。Office 自动转换及缺少可信隔离来源的历史预览已暂停；页面明确显示“隔离转换尚未开放”，仍可下载原件并发表整件批注。首轮审阅人只需要浏览器处理文本成果；Office 原件的内容检查目前仍可能需要外部工具，应如实记录这项切换成本。

进入任务的“交付与复核”，从文件卡“请同事审阅”打开审阅页。批注针对准确文件版本；修订和复核在同页完成。当前浏览器自动验收可以在仓库根目录运行 `pnpm test:e2e:delivery`：它使用临时数据和确定性模型回放，测试结束即清理，不能替代下面的真人体验或长期使用实例。

每次真人体验填写实际提交、地址和启动方式。不要把本次自动验收时间当作真人体验时间，也不要将本手册中的 `not_run` 改成通过，除非真的完成并记录该轮。

## 第一轮：本人双账号，三个可执行案例

这一轮允许照着按钮步骤操作，目标是找入口、状态和恢复问题。使用真实模型或手头真实产物；内容可以脱敏。三个案例的目标与材料先填好，**以下情境是试用脚本，不是已经发生的用户需求证据**。

### 案例 1：正常审阅、修订与复核

建议从自己近期一项小型交付开始，例如把接口变更说明交给同事继续集成，或把已有资料整理成可供决策的短报告。首轮优先使用可直接阅读的文本成果，先验证交接，不把格式适配混入主要判断。

1. A 建立或打开任务，确认自己为责任人并接受任务。填写真实目标、约束、验收条件及尚未确认的问题；需要任务约定时，确认这一版后再开始执行。
2. A 使用 Agent 生成一份候选成果，亲自检查内容、依据及限制，再显式发布。切到 B，确认只能看到已发布成果，不能看到 A 未发布的候选名称、正文或私有现场。
3. B 从任务或审阅入口打开准确文件版本。先看“成果依据”，尝试说明：这份成果来自哪次执行、采用什么约定、记录了哪些固定材料、哪些说明仍待核实。找不到的内容记为未知，不自行从最新任务状态推断。
4. B 对一项具体问题发表整件或文本批注，必要时回复，并提交本轮意见。意见应让 A 能决定下一步，例如指出缺少的异常情况及其预期，而不是只写“优化一下”。
5. A 在“修订与复核”中选择这次要处理的意见、必要的已发布参考材料及修订方向，点击“固定本轮意见”。先确认此时没有自动启动 Agent。
6. A 检查冻结内容，明确选择续接原产出会话或开始新执行，再点击开始。记录是否理解两种方式的差别，是否需要重新拼接原文、材料或意见。
7. 新产物出现后，A 显式选择它并“关联为本轮新版”，检查后发布。不能凭同名文件猜测新版，也不能把 Agent 自称已处理当成人工复核。
8. B 查看原稿与已发布新版，逐条确认“已解决”或“仍需修改”。若由 A 代替意见作者收口，必须写出理由。最后由真人按任务验收条件决定是否完成任务。

本例结束时记录：B 是否能解释准确版本及验证范围；A 是否重复搬运过意见；新版是否确实对应本轮；是否出现“发布了就算通过”或“Agent 结束就算任务完成”的误解。通过与否以真实动作和解释为准。

### 案例 2：固定以后又收到意见或回复

使用案例 1 的原稿，也可以另取一份真实成果。A、B 事先约定一项原意见和一项确有价值的补充意见，避免为了测试硬塞无意义要求。

1. B 先发表意见 X。A 选择 X、固定本轮意见，暂不开始或让执行处于进行中。
2. B 再发表意见 Y，并给 X 追加一条改变范围的回复，记录它们出现的时间。切回 A，查看当前批次的固定意见。
3. A 说出本轮会处理什么。确认固定内容包含当时的 X 和已有回复，晚到的 Y／新回复没有静默进入本轮；也不能把晚到意见当成丢失。
4. 完成本轮新版并让 B 复核。A、B 明确讨论 Y／新回复是否仍需处理；需要时另建一轮，显式选择，不能改写已启动批次的历史。
5. 从首页或任务重新进入，检查待办和批注筛选能否让人找到剩余工作。若必须靠记忆、聊天提醒或口头重复，逐次记录。

本例结束时记录：有没有漏意见、重复处理、把新回复误认为已交给 Agent、误把旧结论当成覆盖新问题；额外建轮或确认范围花了多少主动操作时间。

### 案例 3：失败后恢复，以及先发布再关联

只在自己的演练任务中制造中断。保持原稿和已固定批次可用，不改他人的环境。两个分支分别记录，不把成功的一个替代失败的另一个。

**分支 A：开始前或读取时失败。**

1. A 准备好本轮修订文字和明确的执行目标。在点击开始前，主动让自己的执行设备暂时离线，再尝试开始；或在读取审阅内容时短暂断开本浏览器网络。
2. 记录页面是否解释失败、是否保留已有文字和选择、是否误显示“已经开始”或“没有依据”。设备不可用时不应自动换到别人的环境。
3. 恢复网络或设备，先查看本轮状态，再重试原动作。结果未知时先确认已有执行，不能靠连续点击解决。
4. 检查本轮是否只对应一次有效启动；若已收到执行失败终态，记录真实失败原因，再明确安排后续修订。区分“未启动，需要重试”和“已经运行后失败，需要新的处理”。

**分支 B：从原有文件入口先发布。**

1. A 完成本轮执行，先通过任务中原有的文件检查／发布入口发布该次产物，暂不在修订面板关联。
2. 回到原稿的“修订与复核”，显式选择本轮执行已经发布的成果并关联，不按文件名自动推断。
3. B 查看关联后的已发布新版并逐条复核。如果页面找不到关联入口，记为阻塞；不要重跑模型或复制文件来掩盖缺口。

本例结束时记录：恢复是否需要重写、重复解释或重新运行；是否多出不明来源的执行；先发布的成果能否继续完成同一个闭环。

## 第二轮：真人双人交接，与现有工具交叉比较

### 人与任务

邀请一位真实协作者，选近期确实需要交付给对方继续处理的小任务。先写清楚：A 要交付什么，B 接手后要做什么，什么证据足以判断 B 已正确理解并继续工作。不要只让 B 评价界面好不好看。

准备两个内容不同、工作量相近的任务包，例如两组不同接口的集成说明，或两份相近资料的分析与后续建议。尽量对齐材料量、交付格式、领域熟悉度、所需判断和验收要求，不重复同一道题以免第二次靠记忆。

两种方式：

- **现有方式**：团队平时的即时通讯＋个人 Agent＋文档／仓库。允许正常使用搜索、总结、交接模板、批注、文件链接和脚本；不能故意削弱这个基线。
- **WhalePod**：使用本轮交付闭环；B 需要跨任务继续时，再用已发布交接版本、接收理解和固定输入。凡是需要额外打包、导入或配置的劳动都计入。

先让两人练习一次 WhalePod 的必要动作，练习与安装时间单独记录。正式两题由同一个人承担 A、另一个人承担 B，比较同样的角色成本；顺序在开始前抽签选择“现有方式→WhalePod”或相反。有第二组相近任务时换顺序，条件允许再交换角色。只有一对参与者时，顺序和学习效应仍是限制，不能假装已经消除。

### 怎么进行

1. 开始前，分别记录两人对此任务、工具和模型的熟悉程度。验收要求在看成果前固定；两种方式都允许正常提问，不要求 B 为了显得独立而沉默。
2. A 完成实际产出和交付准备。**计时从 A 为这次协作开始组织要求／材料开始，不能等到文件已经打包好才开始。** 产出阶段与交接阶段分开记，便于看出差异来自模型还是协作。
3. B 从收到交付开始，独立解释：当前版本是什么、哪些要求必须遵守、哪些已经核实、哪些仍未知、下一步准备做什么。由事先写好的要求和实际继续结果判断，不能只用自信程度评分。
4. B 完成一个真实后续动作，例如依据接口说明完成一次集成，或据报告作出可检查的修改／决定。中途需要询问 A、找材料或返工，都保留，不删失败样本。
5. 结束后分别询问 A、B：哪一步本来已有工具就够了，哪一步减少或增加了劳动，下次是否愿意继续用，理由是什么。不要先告诉他们产品应当更高效。

### 记时与质量口径

核心比较是 **双方主动劳动总量 = A 主动投入＋B 主动投入**。包括产出准备、材料打包、检查模型输出、整理／核对依据、发布、找版本、审阅、提问、答复、修订安排、人工复核和误解返工。不能只计 B 的接收时间，忽略 A 为自动化准备材料的时间；两人同时工作时分别计各自劳动，不能把重叠时间只算一次。

另外单列：从开始到正确继续工作的自然经过时间、模型等待、设备／网络等待、一次性安装配置与学习成本、维护成本。等待期间如果人在核对或答复，那部分仍计主动劳动，避免重复计入纯等待。共用部署成本归实际操作者；若试算摊销，必须另写假设，保留原始成本。

两种方式尽量使用接近的模型与现有能力。模型、插件、会话历史或执行环境无法对齐时，记录差异，不把更强模型的收益归因于协作界面。若一个方式没有达到共同验收要求，不能只凭更短时间称其更高效。

|---|---|---|
| 任务、顺序、角色、工具／模型与配置 | 待填 | 待填 |
| A：准备／产出／打包／核对／答复／修订操作分钟 | 待填 | 待填 |

## 个人 Agent 能力与本轮边界

不要求用户停止使用自己的个人 Agent、编辑器、文档和仓库。现有方式允许团队发挥熟练工具的完整正常能力；WhalePod 体验中保留哪些习惯、为了跑通闭环改变了哪些习惯，逐项记下。

当前“冻结意见→明确启动修订”的可追溯执行走 WhalePod 已配置的 Agent、设备及工作目录。**尚无外部个人 Agent 会话／交付物自动导入或批注自动回写能力。** 不把个人工具里未记录的工作伪装成 WhalePod 已自动获得的执行依据。若现有模型、插件或工作方式无法平移，记录它的损失和迁移成本；不能先削弱基线，再以顺利跑通作为替代能力的证明。

这一轮暂缓区域批注、Office 原生修订语义、外部 Agent／即时通讯／文档平台集成和自动质量裁决。现有文本批注、整件意见、发布后只读预览或下载能否支持任务，按实际版本记录；不要为覆盖所有格式扩展第一轮范围。需要离开 WhalePod 才能完成的重要判断也要记录，后续再决定是否值得承接。

## 体验后如何决定下一步

先修会让人丢意见、认错版本、误解验证范围、重复启动或无法恢复的具体问题。若 B 省时但 A 花了更多劳动，不能据此判为团队提效；应回到新增操作逐项删减或自动整理，并继续由真人核对。若两人已经能用现有工具同样省事，保留该结果，收窄目标场景。

首轮产出是三个案例的真实问题清单；第二轮产出是配对的双方投入、质量与误解记录。未开始保持 not_run，无法比较写明原因，空字段不补成成功结果。
